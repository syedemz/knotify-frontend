ISSUE F-1: Story 3.4 calls a function that doesn't exist by that name
---------------------------------------------------------------------

WHAT THE PLAN SAYS:
"On the Start button, call useOnboardingDraft().advance(firstCheckpoint) — that sets the checkpoint and moves the wizard forward."

WHY THAT'S BROKEN:
Back in phase 2, we built two separate tools inside useOnboardingDraft:

  1. advance(pageNumber)                          — moves the wizard forward by one page. Takes a NUMBER.
  2. advanceWithCheckpoint(pageNumber, marker)    — moves forward AND drops a checkpoint marker. Takes a number AND a marker.

The plan is asking us to call the FIRST tool but pass it the argument for the SECOND. It's like asking a bartender: "make me a drink — bourbon." The word "bourbon" is a liquid name, not a drink order. If we do exactly what the plan says, we'd pass the string "firstCheckpoint" into a function expecting a page number, and the wizard would either crash or think it needs to jump to page NaN.

ANALOGY:
Imagine a two-button elevator. Button A is "go up one floor". Button B is "go up one floor AND remember you passed this landing so we can drop you back here if you get lost." The plan says "press Button A, and while pressing it, say the word 'landing'." Button A doesn't listen to words. You have to press Button B, and tell it which floor AND which landing.

WHAT THE FIX LOOKS LIKE:
Change the AC to: "call useOnboardingDraft().advanceWithCheckpoint(9, 'firstCheckpoint')" — 9 because Page 9 is what comes after Page 8, and 'firstCheckpoint' is the marker name we agreed on in phase 2.

CONFIRM: Yes please do the fix

ISSUE F-3: Story 3.2's "sanitize" function has no definition, so username generation is guesswork
-------------------------------------------------------------------------------------------------

WHAT THE PLAN SAYS:
"Generate the username as: sanitize(first_name) + sanitize(last_name) + <4-digit alphanumeric>"

WHY THAT'S BROKEN:
"Sanitize" is jargon that could mean five different things, and each version produces a different username. The plan never picks one. And "4-digit alphanumeric" is similarly slippery.

Say the user types first name "Marie-Claire" and last name "O'Brien". What's the username?

  - Version A (lowercase + strip everything non-letter):    marieclaireobrien + 4 chars
  - Version B (lowercase + keep letters and hyphens):       marie-claireo'brien + 4 chars   (has an apostrophe — Cognito might reject)
  - Version C (preserve case + strip):                      MarieClaireOBrien + 4 chars
  - Version D (strip diacritics too, so "Zoë" → "Zoe"):     zoe...

And "4-digit alphanumeric" — is that:
  - 4 digits (0-9), like "7291"?
  - 4 characters from letters and numbers, like "a3f9"?
  - Case-sensitive letters, like "aB3F"?

Each variant is a different pattern the builder has to invent, and if they invent something the wrong way, we'll only find out much later when phase 11's final PATCH to the backend collides with Cognito's username rules or produces usernames the backend rejects.

ANALOGY:
The plan says "build a mailbox — paint it a nice color." "Nice" isn't a color. The painter has to pick — red, blue, teal? — and then you're stuck with whatever they picked. Better to say "paint it #1E88E5 blue."

MY RECOMMENDATION:
Create a new file Helper/usernameHelper.ts with two named, testable functions:
  - sanitizeNamePart(s) → lowercase the input, strip everything that isn't a-z (so spaces, hyphens, apostrophes, accents all vanish)
  - generateUsername(first, last) → sanitizeNamePart(first) + sanitizeNamePart(last) + 4 random chars from [a-z0-9]

That gives us a Cognito-safe, deterministic pattern.

ANSWER: Please crea the usernameHelper.ts with the recommendations

QUESTIONS:
  Q3a. Is lowercase + strip-non-letter the right rule for names, or do you want to preserve accents/case? please use lowercase + strip-non-letter should suffice
  Q3b. Is [a-z0-9]{4} the right suffix, or do you specifically want [0-9]{4} (only digits) — which reads friendlier ("marieobrien7291")? please use [0-9]{4} (only digits)
  Q3c. Should the username helper live at Helper/usernameHelper.ts, or bundled into the existing Helper/validationHelper.ts? create Helper/usernameHelper.ts

ISSUE F-6: Story 3.3's validateBirthday can't be tested reliably
----------------------------------------------------------------

WHAT THE PLAN SAYS:
"validateBirthday(iso) returns a LabelKey or null."
"Unit tests cover boundary cases at 17y364d, 18y0d, today, 1899, 1900."

WHY THAT'S BROKEN:
The two helper functions used INSIDE validateBirthday (isAtLeast18 and isNotFuture) each accept a "today" argument, which is how we test what happens on someone's 18th birthday exactly — we hand the function a pretend "today" of 2044-03-15 and a birthday of 2026-03-15 and check what it says.

But the composite validateBirthday(iso) as written does NOT accept "today" — it presumably reads the real system clock. That means our boundary tests will be flaky: a test that runs today (2026-07-23) will produce a different answer than the same test run tomorrow, and the "18y0d" boundary test can only ever be correct on exactly one day per year.

ANALOGY:
You want to test "does this alarm clock go off at 7am?" The right test is: set the clock's belief about "now" to 6:59am and check that it stays quiet, then to 7:00am and check that it rings. If the alarm clock refuses to let you fake the time and only ever reads the real wall clock, you literally have to be there at 6:59am on test day. That's not a test — that's an ordeal.

WHAT THE FIX LOOKS LIKE:
Change the signature to validateBirthday(iso: string, today?: string): LabelKey | null. Default today to the real current date when not provided (so production code stays clean), but let tests inject any date they want.

CONFIRM: make today an injectable parameter? Yes

ISSUE F-8: Story 3.1's "not sent as writable on retry navigation" clause has nothing to plug into
-------------------------------------------------------------------------------------------------

WHAT THE PLAN SAYS:
"Once sex is selected, the field is treated as immutable-after-set (recorded by Helper/immutableFieldHelper.ts predicate; not sent as writable on retry navigation to this page)."

WHY THAT'S SCOPE CREEP:
There are TWO things being asked here:

  1. Build a predicate function that says "is this field immutable-after-first-write?" — for sex, the answer is yes.
  2. Make sure that when we retry submitting the user's profile, the sex field isn't included as a writable field.

The FIRST thing is small and belongs in phase 3 — it introduces the predicate and its unit tests.

The SECOND thing requires there to be a "profile PATCH builder" that consumes the predicate and decides what fields to send to the backend. That builder doesn't exist yet. It gets built in phase 11 (the final PATCH page). So the "not sent as writable on retry navigation" clause has NOWHERE to attach in phase 3 — the only piece of code that would honor it doesn't exist yet.

If we leave the clause in, the builder will either (a) build a placeholder PATCH filter with no consumer, which is dead code, or (b) invent some ad-hoc "don't send sex twice" logic in the screen itself, which is the wrong layer and will collide with whatever phase 11 does properly.

ANALOGY:
The plan says "install a smoke detector, and wire it to the fire sprinklers." Fine — but the sprinklers haven't been installed yet, they're in phase 11. So we should install the smoke detector, leave the wire coiled up, and finish the connection when the sprinklers arrive.

MY RECOMMENDATION:
Keep the predicate + its unit tests in phase 3. Strike the second clause. Add a note to phase 11's PRD: "PATCH-builder must call immutableFieldHelper.isImmutable() to skip immutable fields on retry submissions."

CONFIRM: strike the second clause from Story 3.1 AC, defer PATCH-time filtering to phase 11? Yes please do it

ISSUE F-9: The plan never says "update the wizard's page pointer" as pages 5-8 advance
--------------------------------------------------------------------------------------

WHAT THE PLAN OMITS:
Each screen (pages 5, 6, 7, 8) should call draft.advance(nextPageNumber) as the user moves forward, so the draft's currentPage field stays coherent. None of the ACs actually say this.

WHY IT MATTERS:
The draft has a currentPage field that phase 2 wired up. It's used by:
  - the checkpoint-resume logic (which page do I mount when the user relaunches?)
  - the progress-bar reads (which page is the user on?)

If pages 5-8 navigate but forget to advance the draft, the progress bar and resume logic will lag behind or read stale values. It's the kind of bug that doesn't show up in a happy-path test but manifests as "why does the progress bar say 33% when I'm on page 7?" three weeks later.

ANALOGY:
Every time a train leaves a station, someone needs to update the station board. If page 5 → 6 doesn't update the board, the arrival board at the next station still says "Now approaching: Page 5" even though the train left an hour ago.

WHAT THE FIX LOOKS LIKE:
Two options:
  A. Add a line to EACH story (3.1, 3.2, 3.3, 3.4) saying "on continue/select, call draft.advance(<next-page-number>) before navigation."
  B. Add ONE shared "phase conventions" section at the top of the PRD saying "every screen calls draft.advance(nextPage) on continue" and don't repeat it per story.

CONFIRM: add the ACs (and choose option A or B)? Go with Option A


ISSUE F-10: The plan never verifies the draft's sex field is properly typed
---------------------------------------------------------------------------

WHAT THE PLAN OMITS:
Story 3.1 will write "Male" or "Female" into the draft's sex field. But no AC says the sex field's TypeScript type should be 'Male' | 'Female' | undefined (a strict union). If it's currently typed loosely as string, the plan quietly widens the schema without anyone noticing.

WHY IT MATTERS:
Strict typing catches bugs. If sex is typed as string, then in phase 7 someone could accidentally write sex = "male" (lowercase) and TypeScript would say fine, but the backend would reject it. If sex is typed as 'Male' | 'Female', TypeScript catches the typo at write-time.

ANALOGY:
A shipping form has a "country" field. If the field is a free-text box, someone types "USA", "U.S.A.", "United States", "america" — chaos. If it's a dropdown limited to exact country names, the data stays clean. TypeScript is that dropdown for the codebase.

WHAT THE FIX LOOKS LIKE:
Add to Story 3.1 AC: "Verify OnboardingDraft.sex is typed 'Male' | 'Female' | undefined; if it's currently typed string, tighten it."

CONFIRM: add the type-tightening AC? Yes

ISSUE F-11: Story 3.1 doesn't say what happens if the user back-navigates to page 5 after picking a sex
--------------------------------------------------------------------------------------------------------

WHAT THE PLAN OMITS:
Story 3.1 says the sex tile auto-advances on tap. It also says the field is "immutable-after-set" — but that word is ambiguous between "immutable on the backend after the profile is saved" and "immutable in the UI the moment the user first taps it."

Concrete scenario the plan doesn't handle:
User taps Male → auto-advances to page 6 → hits the back button → arrives on page 5 again. Now what?

Three reasonable behaviors:
  A. Both tiles remain tappable. Tapping Female overwrites the draft's sex and auto-advances again.
  B. The Male tile stays highlighted and locked; Female is grayed out. To fix a misclick the user must cancel onboarding entirely.
  C. Both tappable, but changing the choice pops a confirmation dialog ("Are you sure? This can only be set once.").

RESOLUTION (2026-07-23):
Going with Option A — freely editable during onboarding. Rationale: a misclick shouldn't be punished with a full onboarding restart. The backend-side immutability (Question B in the earlier discussion) still applies once the profile is committed at phase 11's final PATCH — but during the onboarding form itself, the user can freely revise any field by back-navigating.

WHAT THIS MEANS FOR THE PRD:
  - Story 3.1 gets a new AC: "Back-navigating to page 5 leaves both tiles tappable. Tapping the opposite tile overwrites the draft's sex field and re-triggers auto-advance to page 6."
  - Screen wiring test adds a case: seed the draft with sex=Male, mount the screen, tap Female, assert draft becomes sex=Female and navigation fires.

  This also clarifies F-8: the immutableFieldHelper predicate is ONLY consulted at phase 11's PATCH-build time (deciding what to send to the backend). It's never consulted by page 5 itself. During the form, all fields are freely editable.
