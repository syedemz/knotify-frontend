What this file is: the brainstorm file lists 10 "blocking" problems and 4
"advisory" problems with the phase 16 plan. This file explains each one the

PART A — BLOCKING PROBLEMS (fix these before dispatching the phase)
================================================================================

--------------------------------------------------------------------------------
BLOCKING 1 — The friend-request plumbing nobody drew on the blueprint
--------------------------------------------------------------------------------

The problem:
    Phase 16 is supposed to connect the app to the real backend for everything
    friend-related: sending friend requests, accepting them, declining them,
    cancelling them. But if you read the 10 stories in the plan, NOT ONE of
    them actually says "write the code that talks to the friend-request
    endpoints." The plan says "build the Friends list," "build the chat
    backend," "build Blocks" — but the actual accept/decline/send/cancel
    plumbing is just... missing. The plan's own author even wrote a note at
    the top saying "the brainstorm must add stories for this" — so this is a
    known hole that was deferred to right now.

Analogy:
    Imagine someone handing you blueprints for a house. The plans show you
    the kitchen, the bathroom, the front porch — all beautifully drawn. But
    there's no plan for the plumbing. The architect's note says "the plumber
    will figure it out when they show up." That's where we are. The buttons
    exist (Accept, Decline, Send Request), the screens exist, but the pipes
    that carry those actions to the backend were never drawn.

Why it matters:
    Without this, every button we add in later stories is cosmetic. Tapping
    "Accept" would do nothing real — it'd update a mock in local memory and
    forget everything on app restart. The subsequent chat + modal stories all
    assume these mutations work, so they'd fail or stall when dispatched.

Options:
    A. Add three new stories (16.FR1, 16.FR2, 16.FR3) covering the REST
       endpoints, the mutation hooks, and rewiring the modals + tearing out
       the mock FriendshipProvider.
    B. Try to cram all of that into story 16.1 or 16.8 as "notes" and hope
       the subagent figures it out.
    C. Punt friend-request wiring to phase 17 and just do friends list +
       chat + blocks in phase 16.

Recommended: A.
    Option B is a trap — stories are already large; stuffing more in makes
    the subagent's job ambiguous and causes partial ships. Option C sounds
    appealing but breaks phase 16's core promise (the PRD title itself says
    "Friend requests, friends, chat backend, blocks") and leaves users in a
    worse state than today (because we'd rip out the mock before the real
    thing exists). Add the three stories. Phase stays coherent.

ANSWER: Option A

--------------------------------------------------------------------------------
BLOCKING 2 — The plan references a tool we don't use
--------------------------------------------------------------------------------

The problem:
    Several stories in the plan say "add a handler to services/api/mocks/
    handlers.ts" and reference a library called MSW (Mock Service Worker).
    But MSW was ripped out of this project months ago because it doesn't
    work on React Native's JavaScript engine (Hermes). The actual mock
    system is a different file called mockRequest.ts. So the plan is
    describing a kitchen appliance that was donated to charity last year.

Analogy:
    Your plan says "use the microwave to reheat the leftovers." But the
    microwave broke six months ago and you now use the toaster oven. A
    helper reading the recipe will stand in your kitchen confused, looking
    for a microwave that isn't there.

Why it matters:
    A subagent reading the PRD would create files that don't fit, or spend
    time trying to find/install MSW, or worse — ship code that doesn't run.
    Cheap to fix, expensive to leave in.

Options:
    A. Edit every PRD mention of MSW or handlers.ts to say "extend
       mockRequest.ts" instead.
    B. Reinstall MSW and make the plan accurate.
    C. Leave it alone and hope the subagent notices.

Recommended: A.
    MSW was removed for a real reason (incompatible with Hermes). Bringing
    it back is a lot of work for no benefit. Option C is lazy — the mock
    layer touches almost every story, so the subagent WILL stumble. Option
    A is a 10-minute edit.

ANSWER: Option A, and please remember we not mocking anything now, we are now building against a real backend

BLOCKING 3 — Chat in mock mode has no mock to run against
--------------------------------------------------------------------------------

The problem:
    The app has a "mock mode" for developing without the real backend. REST
    calls get intercepted and return fake data. But chat uses a DIFFERENT
    protocol (AppSync / WebSockets), and no story in the plan creates the
    fake version of AppSync. So the moment someone turns on mock mode and
    opens a chat, there's nothing to connect to — the chat screen would hang.

Analogy:
    You've built a flight simulator so pilots can practice without renting a
    real plane. The cockpit is simulated, the runways are simulated — but
    the air traffic control radios are still trying to reach the real tower.
    When the trainee picks up the radio, they get silence.

Why it matters:
    If chat only works against the real cloud, then every developer on this
    project needs real AWS credentials just to look at the chat UI. That's
    slow, expensive, and blocks offline development.

Options:
    A. Add a new story (16.M1) to build a fake AppSync client that emits
       scripted events from a fixture file. Separate flag "isMockAppsync"
       so you can mix real/fake freely.
    B. Expand story 16.3 to include the mock client alongside the real one.
    C. Declare mock mode = "REST only, chat always real." Developers need
       AWS creds to touch chat.

Recommended: A.
    Option B overloads one story with two unrelated things (real client
    AND fake client) — that story becomes a mini-phase on its own. Option C
    punishes everyone who wants to iterate on chat UI. A clean "16.M1 —
    build the mock chat client" story that story 16.4's hook tests can lean
    on is the simplest path.

ANSWER: dont we still have a real appsync on the backend for real chat functionality, if not please let me know , then we need to build it, as far as i know
it has already been built , i can provide temporary credentials for you to check

BLOCKING 4 — Two libraries fighting over the same light switch
--------------------------------------------------------------------------------

The problem:
    The AWS Amplify library (which we use for login AND chat) gets
    "configured" once at app start. The login code already does this.
    Phase 16 needs to also tell Amplify how to configure CHAT. But the
    login code has a guard that says "if you've already been configured,
    don't do it again" — so the chat-configure call would be silently
    skipped. Also, the plan says the AppSync code lives at services/api/
    but on disk it's actually at services/graphql/. Small path drift, but
    worth catching before a subagent creates a duplicate file in the wrong
    place.

Analogy:
    Imagine a thermostat that can be set once per day. Your spouse already
    set it to 70°F this morning for the living room. You come home and try
    to set it to 68°F for the bedroom, but the thermostat says "sorry,
    already set today." You need either a thermostat that accepts multiple
    zones, or a shared ritual where whoever sets it first sets it for
    EVERY room at once.

Why it matters:
    If the second configure call is silently skipped, chat would fail to
    connect and the error message would be confusing ("endpoint not
    configured" with no hint why).

Options:
    A. Refactor the configure logic into one shared module that both login
       and chat contribute to. Called exactly once at startup with the full
       config for both.
    B. Call Amplify.configure twice and trust Amplify v6's documented
       "merge, don't overwrite" behavior.
    C. Have the chat module reset the guard and reconfigure from scratch.

Recommended: A.
    It's the cleanest. Option B relies on behavior that needs verification
    in Amplify's docs AND could change in a patch release. Option C is
    fragile — any future "configurable thing" would need the same reset
    dance. Also fix the path: use services/graphql/ (where the stub already
    is), update the PRD AC to match.

ANSWER: Option A

BLOCKING 5 — Which ID gets passed around: user ID or room ID?
--------------------------------------------------------------------------------

The problem:
    When you open a chat today, the code passes along the other person's
    user ID ("friendUserId") and the chat screen figures out which room to
    show. But the real backend uses "room IDs" — a separate identifier for
    each conversation. Which one should the app use going forward?

    The plan says "decide during story time" — but THREE different stories
    (the chat list, the chat room, the deep-link) each need to know the
    answer. If each story's subagent picks independently, you'd end up with
    inconsistent decisions and have to redo one of them.

Analogy:
    You're running a hotel. Should guests ask for rooms by "Mr. Smith's
    room" or "Room 204"? Either works, but if the front desk uses names and
    the housekeeping staff uses numbers and the booking system uses a mix,
    you get chaos. Pick one convention and stick with it before you print
    the signs.

Why it matters:
    If you don't decide now, you end up refactoring in the middle of the
    phase after one subagent chose names and another chose numbers.

Options:
    A. Switch to room IDs everywhere. Update the chat screen's address bar
       to expect a room ID, and have the "open chat with user" helper do
       the user-ID-to-room-ID lookup behind the scenes.
    B. Keep user IDs in the app and have the deep-link code reverse-lookup
       room IDs → user IDs when needed.
    C. Accept both and let each screen decide.

Recommended: A.
    This is how the real backend speaks. The user-ID path is an artifact of
    the mock world where "one friend = one chat room, automatically." Using
    room IDs now is a cleaner mental model, and the "open chat with user"
    helper already exists (openChatRoom.ts) and can hide the lookup inside.
    Only one screen changes type signatures. Option B keeps lipstick on the
    pig. Option C is how you get bugs.

ANSWER: Go with option A

--------------------------------------------------------------------------------
BLOCKING 6 — The deep-link scaffolding is a shell, not a foundation
--------------------------------------------------------------------------------

The problem:
    "Deep links" let you open the app to a specific place from outside — tap
    a link in a push notification, land directly in a chat room. The current
    deep-link config file is literally empty: no URL prefixes, no route map.
    The phase 16 story says "add one deep-link for chat rooms" — but that's
    like saying "add one hallway" to a house with no walls. You have to
    build the walls (the URL prefix "knotify://" and the overall route
    table) at the same time.

    There's also a loose end: elsewhere in the app, the "share profile"
    button generates knotify://profile/<user_id> links, but no code resolves
    them. Phase 16 might as well wire that up too since the scaffolding
    effort is the same.

Analogy:
    You're putting up a mailbox in a vacant lot. "Add a mailbox" is three
    minutes of work — but first you need an address, a driveway, and a
    road. Building just the mailbox makes no sense until the lot has a
    street number.

Why it matters:
    A subagent given "add one deep link" might add just that one and leave
    the config half-built, meaning chat links work and profile links don't
    — with no explanation in the code of why.

Options:
    A. Rescope story 16.7 to bootstrap the whole deep-link config end-to-
       end: prefixes, nested route map, both chat AND profile links.
    B. Leave 16.7 narrow, accept that profile share links stay broken this
       phase.
    C. Add a separate story just for deep-link scaffolding, keep 16.7 to
       chat only.

Recommended: A.
    The scaffolding effort is identical whether you wire one route or two.
    Shipping a half-working deep-link system is worse than shipping either
    nothing or the full thing. Option C is fine but creates unnecessary
    story-count inflation.

ANSWER: We will deep links in a different phase, add it to phase 17 prd for now and skip this one phase 16

BLOCKING 7 — The modal buttons lose information
--------------------------------------------------------------------------------

The problem:
    When a friend request arrives, a modal pops up with "Accept" and
    "Decline" buttons. Today, tapping Accept fires a callback that includes
    the SENDER'S user ID. But the real backend needs the REQUEST'S ID (each
    friend request has its own unique identifier, separate from who sent
    it). So the modal is literally not passing along the piece of info the
    backend will demand.

    Similarly, the "Request Accepted" modal's "Say hi" button passes NOTHING
    at all — the current code works only because the host screen hardcodes
    Mehvish as the one person this modal ever displays for.

Analogy:
    The waiter brings your receipt and asks if you want to tip. You say
    "yes, 20%." But the waiter only writes down "yes, 20%" — not WHICH
    table or WHICH order. In today's test setup there's only ever one
    table, so nobody noticed the omission. But the real restaurant has 40
    tables.

Why it matters:
    When real subscription events start flowing in, "Accept" calls would
    either fail entirely (backend demands request_id) or accept the WRONG
    request. And "Say hi" would always navigate to Mehvish regardless of
    who actually accepted.

Options:
    A. Change the modal callbacks to carry the full information: Accept
       passes (userId, requestId); SayHi passes (acceptorUserId). Hosts
       update accordingly. Covered by story 16.FR3.
    B. Have the host look up the missing info by cross-referencing other
       state.
    C. Hardcode something and hope for the best.

Recommended: A.
    Option B spreads knowledge about request shape across many hosts; the
    modal already has the data in scope, so passing it is one-line changes.
    Option C is how you get bug reports where the wrong person gets friended.

ANSWER: Option A

BLOCKING 8 — Promising status icons we can't actually deliver
--------------------------------------------------------------------------------

The problem:
    The plan says chat bubbles should show the three WhatsApp-style status
    ticks: sent (one check), delivered (two checks grey), read (two checks
    blue). To make these real, you need THREE separate real-time
    subscriptions from the server — one for new messages, one for delivery
    receipts, one for read receipts. The plan only wires up ONE of them
    (new messages). So the AC is promising something we literally don't
    have the data for.

Analogy:
    You open a restaurant and the menu says "Guaranteed in under 30
    minutes." But you forgot to put clocks in the kitchen. You might DELIVER
    food fast, but you can't honestly promise or verify the guarantee.

Why it matters:
    A subagent reading this AC will either (a) fake the status icons by
    guessing from client-side state (misleading UI), or (b) scope-creep and
    try to add the missing subscriptions mid-phase, blowing out the budget.

Options:
    A. Rewrite the AC: "sent ticks show for every sent bubble; delivered/
       read ticks are stubbed and tracked separately as a future story."
    B. Expand the phase to wire up all three subscriptions.
    C. Drop the status icons entirely until the full feature lands.

Recommended: A.
    Option B triples the chat scope — it's a legitimate follow-up but not
    now. Option C makes the UI feel incomplete. Option A is honest: the
    bubble shows "sent" (a truthful statement), and the richer indicators
    get their own phase later. Users won't miss what they never saw.

ANSWER: both option A and B, do option A for now so that we can test chatting and then Option B add more stories to phase 16 which have expanded scope for all 3 subscriptions,
all chat functions should be done in phase 16

BLOCKING 9 — The cleanup check doesn't cover enough ground
--------------------------------------------------------------------------------

The problem:
    Throughout the codebase, mock/fake code is tagged with a special
    comment (TODO(mock-only)) so we can grep to find leftovers. Story 16.5
    has a check at the end: "make sure no mock comments remain in the chat
    folders." Fine for chat — but there are a LOT of mock comments in the
    friendship folder too, and those ALSO need to be cleaned up this phase.
    The check as-written would pass even if the friendship mocks are
    half-torn-out.

Analogy:
    You're moving out of an apartment and the landlord's final checklist
    says "make sure the living room is empty." You pass the check — but
    you left all your furniture in the bedroom. Deposit lost.

Why it matters:
    Mock code left behind after real code lands is confusing at best and
    a source of bugs at worst (two code paths do the same thing differently).
    The grep check is the automated enforcement — if it's too narrow, the
    enforcement is theater.

Options:
    A. Expand the grep scope to cover friendship + friendRequests folders
       too. Add it as a phase-level AC (either on 16.5 or on the new
       16.FR3).
    B. Keep the check narrow and trust code review to catch leftovers.
    C. Drop the check entirely.

Recommended: A.
    Takes 30 seconds to fix, prevents an entire class of subtle bugs. Option
    B relies on human memory; humans forget. Option C surrenders the gain.
ANSWER: Option A

--------------------------------------------------------------------------------
BLOCKING 10 — Two stories racing to edit the same file
--------------------------------------------------------------------------------

The problem:
    Story 16.5 DELETES the old chat data provider. Story 16.6 REWIRES the
    chat screen to use something else. Both stories say they depend on
    story 16.4, but neither says they depend on EACH OTHER. If the
    subagent runs 16.6 before 16.5, the chat screen still imports the old
    provider — but 16.6 is supposed to remove that import. If 16.6 runs
    AFTER 16.5, the chat screen briefly can't compile (the old provider was
    just deleted, but 16.6 hasn't replaced the import yet).

Analogy:
    Two roommates. One is scheduled to toss out the old couch, the other
    is scheduled to bring in the new couch. Nobody said who goes first. If
    the old couch leaves on Monday and the new one shows up Friday, you
    sit on the floor all week. If they bump into each other at the door,
    you have two couches and no room.

Why it matters:
    The subagent that runs second will encounter a broken file and either
    stall or improvise — neither is great.

Options:
    A. Make story 16.6 explicitly depend on 16.5. Old couch out first,
       then new couch in.
    B. Merge 16.5 and 16.6 into one bigger story so the whole swap is
       atomic.
    C. Leave the dependency implicit and trust the subagent.

Recommended: A.
    Smallest edit (one line in the PRD) with clearest effect. Option B is
    fine but produces a larger single story that's harder to review. Option
    C is how you get the "worked on my first try, broken on the second run"
    class of bug.

ANSWER: Option A

ADVISORY 11 — The real-time listener doesn't have a home yet
--------------------------------------------------------------------------------

The problem:
    Story 16.8 says "mount a subscription listener at the root of AppTabs
    (or some shared root)." But no listener component exists yet, and the
    plan doesn't say what it should be called, where exactly it should
    mount, or how it should hold modal state. A subagent would have to
    invent the pattern on the fly.

Analogy:
    The blueprint says "install a doorbell somewhere near the front door."
    OK — but on the door frame? Next to the mailbox? At shoulder height or
    chest height? Does it need its own wiring run or share the porch
    light's? Not blocking, but worth specifying before the electrician
    shows up.

Why it matters:
    If it's not specified, two different subagents reading the same PRD
    would invent two different placements and the code review turns into a
    design argument.

Options:
    A. Add a one-paragraph note to the PRD naming the component (e.g.
       FriendRequestSubscriptionListener), its mount point (just above
       Tab.Navigator inside AppTabs), and its state model (local useState,
       or a dedicated context).
    B. Leave it to the subagent.

Recommended: A. 20 seconds of PRD text saves 20 minutes of review debate.

ANSWER: Option A

ADVISORY 12 — The chat-room overflow menu is a no-op; now it needs a "Block"
--------------------------------------------------------------------------------

The problem:
    The triple-dot menu in the top-right corner of a chat room is wired to
    a function that just logs to the console. Story 16.10 says "add a Block
    action in the overflow menu" but the overflow menu doesn't functionally
    exist yet. Is the subagent supposed to build a full menu framework? Or
    just a single-item action sheet?

Analogy:
    You ask a contractor to "hang a coat on the hook." Fine — but there's
    no hook yet. Should they install a single simple hook, or a 4-prong
    rack, or a closet? Specify or get a surprise.

Why it matters:
    Over-scoping leads to lost time. Under-scoping leaves a menu button
    that's still mostly broken.

Options:
    A. Add an AC: "single-item action sheet for this phase; full menu is
       deferred."
    B. Leave undefined and get what the subagent chooses.

Recommended: A.

ANSWER: Option A

ADVISORY 14 — A stale note in the assistant's memory about a broken branch
--------------------------------------------------------------------------------

The problem:
    The AI assistant has a note in persistent memory saying "a branch
    called feat/real-deck-from-backend has broken code that needs fixing."
    That branch's work was actually shipped through a DIFFERENT branch and
    merged last week. The old note is now misleading.

Analogy:
    Your car's dashboard still shows a tire pressure warning, but you
    actually pumped up the tire last month — the sensor just didn't reset.
    Harmless now but could confuse the next person who glances at the
    dashboard.

Why it matters:
    Low — won't affect phase 16 execution. But could cause a future session
    to try to "fix" code that's already fixed.

Options:
    A. Delete the stale memory entry.
    B. Leave it.

Recommended: A. Cheap to do, prevents future confusion.
ANSWER: Option A
================================================================================
BOTTOM LINE
================================================================================

If we dispatch the plan as-written, blocking items 1, 4, 5 will stall the
subagents immediately. Items 2, 3, 6, 10 will cause partial or inconsistent
ships. Items 7, 8, 9 will create bugs that surface later. None of these are
hard to fix in the PRD — total editing effort is probably 30-45 minutes.
Dispatching first and fixing later costs multiples of that in subagent
retries and cleanup PRs.

The strong recommendation is: address the gaps in the PRD, then re-run
/implement-phase 16.
