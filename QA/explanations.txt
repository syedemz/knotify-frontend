Phase 6 builds pages 15, 16, and 17 of the onboarding wizard:
  - Page 15: pick your current country of residence (with flag + dial code)
  - Page 16: type in your current city
  - Page 17: pick your Kashmir district + type your family's residence address

I audited the plan against the code we actually have today and found 13
issues. They range from "the phase will not build" to "small wording
cleanups." I've numbered them and rated severity. For each one you get
three sections:

  WHAT THE PLAN SAYS  — the exact instruction in the PRD
  WHY IT MATTERS      — what will happen if we don't decide
  YOUR CHOICES        — the options I see, with the recommended one marked

Just tell me the number and letter for each one (e.g., "1: A, 2: B, 3: A")
and I'll update the plan accordingly.

ISSUE 1 — SEVERITY: BLOCKER
    "The plan says show flags — but the flag library isn't installed"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
  Story 6.1 (page 15) says: render each country row with a flag using the
  library "react-native-country-flag".

WHY IT MATTERS
  Imagine a recipe that calls for saffron, but there's no saffron in the
  pantry. You can't start cooking until someone goes to the store.

  We wrote the recipe last month assuming saffron was already on the shelf.
  It isn't. Our "package.json" file (the shopping list of libraries the app
  uses) doesn't mention "react-native-country-flag" at all. So the very
  first thing the subagent needs to do is install it — but the plan doesn't
  tell them to. If they follow the plan literally, they'll try to import a
  library that doesn't exist and the build will fail.

  This is easy to fix — we just need to be explicit about who installs it
  and when.

YOUR CHOICES
  A) [RECOMMENDED] Add a note to story 6.1: "Install react-native-country-flag
     via 'npx expo install react-native-country-flag' as the first step of
     this story; add jest mocking if the tests trip on native imports."
     Then the subagent knows this is part of their job, not a bug.

  B) Install the library right now, outside of any story, and then let the
     subagent proceed. Cleaner separation, one more step for you upfront.

  C) Do nothing and hope the subagent figures it out. (Not recommended —
     they might file a "missing dependency" report instead of just installing.)
  
Answer: Option A

ISSUE 2 — SEVERITY: BLOCKER (but self-resolving)
    "The plan says put the picker in a folder that doesn't exist yet"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
  Story 6.1 says the new CountryPicker component lives at
  "src/features/onboarding/components/".

WHY IT MATTERS
  That folder doesn't exist today. Not a real problem — folders are created
  on the fly — but it's a new organizational convention for this project.
  Until now, reusable UI pieces have lived in "src/components/" (the shared
  catalog). Story 6.1 is quietly introducing a second home: "feature-local"
  components that only make sense inside onboarding.

  Think of it like this: your kitchen has a drawer of general utensils
  (spatulas, whisks) that any recipe might use. This story creates a
  separate little drawer inside the "pasta cabinet" for the pasta-specific
  gadgets that nobody else needs. That's a fine idea — but if we're
  starting a new drawer, we should say so on purpose, not by accident.

YOUR CHOICES
  A) [RECOMMENDED] Keep the plan as-is. This new "feature-local components"
     pattern is a good idea for phase 6 and future phases. The subagent will
     create the folder on the fly. We just acknowledge the pattern is new.

  B) Move CountryPicker into the shared "src/components/" catalog to keep
     one convention. Downside: pollutes the shared catalog with an
     onboarding-only component.

  C) Move CountryPicker inline into Page15CountryScreen (no separate file).
     Downside: 200 lines of picker logic mixed with page-level wiring.

Answer: Option B

ISSUE 3 — SEVERITY: GAP
    "The plan says 'searchable list' but not how the search works"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
  Story 6.1: page 15 renders a "searchable list" of ~200 countries.

WHY IT MATTERS
  "Searchable" could mean many things. Does the user type "pak" and it
  jumps to Pakistan? Does it match anywhere in the word, so typing "tan"
  finds Pakistan AND Kazakhstan? Is it case-sensitive? Does it search
  dial codes too, so typing "+92" jumps to Pakistan?

  If we don't pick, every developer (or subagent) will invent their own
  answer and we'll get inconsistent behavior across the app.

  Analogy: telling someone "make it searchable" is like telling a chef
  "season to taste" — different chefs will make very different dishes.

YOUR CHOICES
  A) [RECOMMENDED] Case-insensitive PREFIX match on country name only.
     Type "pak" → Pakistan matches. Type "tan" → nothing matches (because
     no country name starts with "tan"). Simple, fast, predictable.

  B) Case-insensitive SUBSTRING match on country name. Type "tan" → both
     Pakistan and Kazakhstan match. More flexible but more results per
     keystroke.

  C) Case-insensitive substring match on BOTH country name AND dial code.
     Handles "user knows the +92 but forgot the name" case. Slightly more
     work to implement.
Answer: Option A


--------------------------------------------------------------------------------
ISSUE 4 — SEVERITY: GAP
    "Should we pre-select the user's country based on their phone locale?"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
  Nothing — the plan doesn't mention a default.

WHY IT MATTERS
  Many onboarding apps notice you're in Pakistan and open the country
  picker already scrolled to Pakistan, saving you a tap. But guessing wrong
  can be worse than not guessing — a Pakistani-Canadian user visiting
  Karachi shouldn't have "Pakistan" pre-picked for them.

YOUR CHOICES
  A) [RECOMMENDED] No default. Picker opens at the top (Afghanistan).
     Simplest, no assumptions, no wrong guesses. User taps their country.

  B) Pre-scroll (but don't pre-select) to the device's locale country.
     Middle ground: helpful but doesn't auto-submit.

  C) Pre-select AND pre-scroll to device locale country. Fastest but risky.

Answer: Option A

--------------------------------------------------------------------------------
ISSUE 5 — SEVERITY: GAP
    "The plan says 'letters/spaces/hyphens/apostrophes' — but we already
     have a helper for that; can we reuse it?"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
  Story 6.2 (page 16, city): validate that the city name is
  letters/spaces/hyphens/apostrophes, max 40 characters.

WHY IT MATTERS
  We already have a function called "isValidName" in the codebase that
  does EXACTLY the same character check — but it caps at 35 characters
  (because names cap at 35). Cities can be up to 40. So we can't just
  reuse "isValidName" as-is.

  Analogy: you have a measuring cup that goes up to 35ml. You need to
  measure 40ml. You could get a bigger cup, or you could raise the
  markings on the old one — but you have to pick.

  If we don't pick, the subagent will either (a) reuse isValidName and
  wrongly reject 36-40 character cities, or (b) invent a new helper with
  a name we don't like ("isValidCityName"? "isCity"? "validateCity"?).

YOUR CHOICES
  A) [RECOMMENDED] Add a new helper "isValidCity" in validationHelper.ts
     with "MAX_CITY_NAME_LENGTH = 40". Matches the naming pattern already
     used for jobs, employers, and addresses (MAX_JOB_TITLE_LENGTH etc.).

  B) Generalize "isValidName" to take a max-length parameter and call it
     from both places. More DRY, but changes a shipped function's signature
     (risk of breaking phase 3 tests).

  C) Inline the regex + length check into Page16ResidenceCityScreen with
     no helper. Fastest, but less testable.

Answer: Option A

ISSUE 6 — SEVERITY: GAP
    "'Default preselected Srinagar' — but what does 'preselected' MEAN?"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
  Story 6.3 (page 17, Kashmir district): default preselected "Srinagar".

WHY IT MATTERS
  Two very different things could happen:

  (a) On page load, we quietly write "Srinagar" into the draft AND paint
      the Srinagar row as selected. If the user taps Continue without
      touching anything, "Srinagar" gets saved.

  (b) On page load, we just VISUALLY paint Srinagar as selected, but the
      draft is still empty. Continue is disabled until the user taps
      SOMETHING (even if that's Srinagar itself).

  Option (a) matches what users expect from a "default" — they see it
  selected, they trust it's selected, they hit Continue. Option (b) is
  safer against silent auto-submits but confusing: "why is it highlighted
  if it's not actually chosen?"

  Every OTHER page in the wizard so far (page 5 sex, page 9 religion,
  page 12 education) has NO pre-selection — user must tap. Page 17 would
  be the first exception.

YOUR CHOICES
  A) [RECOMMENDED] Option (a): on mount, if kashmir_district is null in
     the draft, immediately write "Srinagar". Row paints as selected AND
     draft has the value. Consistent behavior. Back-navigation from a
     later page never overwrites the user's real choice.

  B) Option (b): visually highlight Srinagar but keep draft empty. Force
     the user to explicitly tap a district before Continue enables.
     Consistent with the "no pre-selection" pattern from other pages.

  C) No preselect at all. Remove "Srinagar default" from the plan and
     treat page 17 like all the other picker pages.

Answer: Option A


--------------------------------------------------------------------------------
ISSUE 7 — SEVERITY: GAP
    "What characters are allowed in the family residence address?"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
  Story 6.3: multiline TextInput for family_residence_address, max 70
  characters. Doesn't say what characters are allowed.

WHY IT MATTERS
  Addresses in Pakistan and Kashmir include slashes ("H#12/A"), hash
  signs ("Flat #4"), commas, dashes, apostrophes ("O'Malley Road"), and
  house numbers. If we apply a strict letters-only rule, real addresses
  will be rejected.

  Page 11's office_address field solved this the same way: no character
  restriction at all, just a max-length cap. Story 6.3 should probably
  do the same but it doesn't say.

  Analogy: a bouncer at the club door either has a list of "who's
  allowed in" (whitelist) or a list of "who's banned" (blacklist).
  If we skip both, everyone gets in. That's often the right call for
  addresses.

YOUR CHOICES
  A) [RECOMMENDED] No character rule. Only cap at 70 characters. Enable
     autoCorrect. Mirrors office_address from phase 11 exactly.

  B) Whitelist letters/digits/spaces/hyphens/commas/slashes/hash/period/
     apostrophe. More restrictive, might miss weird-but-valid addresses.

  C) Just letters and spaces. Way too restrictive — will reject real
     addresses. (Only listed for completeness.)
Answer: Option A
