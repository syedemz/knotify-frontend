================================================================================
PHASE 13 BRAINSTORM — LAYMAN EXPLANATION OF THE PROBLEMS FOUND
================================================================================

Before I dispatch anyone to write phase-13 code, I re-read the PRD and cross-
checked it against the actual code we already shipped in phases 11 and 12.
I found 2 real problems (blockers), 5 medium-sized things worth locking down
before coding (sharpen), and 4 small notes. Each one below is written plainly,
with an analogy where useful. At the end of each item I list the possible
fixes so you can pick one — or write your own.

Underlying vocabulary refresher (skip if you already know it):

  - "PRD"        = the phase-13 plan file at
                   implementationplan/phase-13-discover.md
  - "story"      = one numbered task inside that plan (13.1, 13.2, ... 13.5)
  - "AC"         = "acceptance criteria" — the checklist inside each story
                   that says "this story is done when X and Y and Z are true"
  - "type"       = a TypeScript declaration that says "an object of this
                   kind has field A of type string, field B of type number",
                   etc. It's a contract the code enforces at compile time.
  - "fixture"    = a fake data file we use during development instead of
                   real backend data (e.g. dummyfemale.json)
  - "component"  = a piece of the UI that renders itself (a button, a
                   section, a card)
  - "provider"   = a React context that holds shared state (e.g. who is
                   logged in). Any screen in the app can "read from" a
                   provider.
  - "deck"       = the stack of candidate profile cards a user swipes
                   through on the Marriage tab. Same idea as Tinder's
                   card stack.
  - "friend"     = a user the current user has already accepted into their
                   circle. Only friends see each other's full profile.
  - "pending request" = another user has asked to be your friend and you
                   haven't accepted or declined yet.
  - "guard"      = a small check at the top of a screen that says "should
                   this screen be visible right now?" and short-circuits
                   to an EmptyState if not.


================================================================================
BLOCKER 1 — The Accept button on OtherProfileScreen will paint the wrong
            screen over its own success toast.
================================================================================

WHAT THE PRD SAYS (story 13.4)

When the current user is viewing Qurat's profile (because Qurat sent them a
friend request), there's an Accept button at the top of the screen. Tapping
Accept does three things, in order:

  (1) Call acceptRequest(qurat_id) on the FriendshipProvider — this
      immediately (a) removes Qurat from the "pending requests" list
      and (b) adds her to the "friends" list.
  (2) Show a snackbar (a small toast at the bottom) that says "Friend
      added".
  (3) Wait 1500 ms, then call navigation.goBack().

Separately, at the top of the same screen, there is a "guard" that says:

  "If source='request' AND the current user does NOT have a pending
   request from this user, hide the profile and show a 'Not authorized'
   EmptyState instead."

That guard exists to prevent someone from typing a random user ID into a
deep link and seeing a profile they shouldn't see.

WHY IT'S A PROBLEM

Step (1) *immediately* flips the FriendshipProvider state — Qurat is no
longer a pending request; she's now a friend. React re-renders the screen.
The guard runs again. And the guard now says: "you don't have a pending
request from Qurat — hide the profile." So during the 1500 ms window where
the user is meant to see the "Friend added" toast, the screen instead flips
to the ugly "Not authorized" EmptyState. Then goBack() finally fires and
the user is dropped back to the Requests list.

ANALOGY

Imagine you walk into a member's club and hand your invitation to the
bouncer. He tears it up (that's how the club knows you're now a member).
But immediately after tearing it up, he looks at your empty hand, notices
you don't have an invitation, and throws you out — even though you just
became a member two seconds ago. The rule is right, but the *ordering*
of the checks is wrong.

FIX OPTIONS

  (a) Broaden the guard. Say: "source='request' is authorized if the user
      currently has a pending request from that user OR is already
      friends with them." This matches the real semantic — once you've
      accepted, you're still authorized to be looking at that profile.
      This is my recommendation. Smallest change, clearest meaning.

  (b) Freeze the guard's decision at mount time using a useRef snapshot.
      The guard runs once when the screen opens and never re-checks.
      Works, but hides a semantic bug behind a technical trick, and means
      a future edit could easily reintroduce the problem.

  (c) Call goBack() FIRST and let the snackbar show on the previous
      screen (Explore Requests). Works but changes the UX contract — the
      snackbar is meant to appear on top of the profile you just accepted
      so it's clear WHO you added.

  (d) Do nothing. The user sees a broken screen for 1.5 seconds and we
      just say "fix later". Not recommended.

    
  Answer: go with option a

BLOCKER 2 — CandidateHero was typed to only accept the OLD single-female
            profile. The deck introduces a new type that won't fit.
================================================================================

WHAT THE PRD SAYS (story 13.3, referencing story 13.1)

Story 13.1 introduces a new TypeScript type called `DummyDeckProfile` for
the five deck cards. It's a shape designed to mirror the backend's future
`deck_view` (a lighter, condensed version of a profile) plus a handful of
extra fields we need to render the About Me / Marriage Intentions / etc.
sections on each card.

Story 13.3 says "reuse CandidateHero as-is" as the top of every deck card.

WHY IT'S A PROBLEM

CandidateHero was written in phase 12 with this signature:

    readonly profile: DummyFemaleProfile;

It ONLY accepts a `DummyFemaleProfile` (the old, single-candidate type
used when we shipped Aisha in phase 12). The new deck-card type
`DummyDeckProfile` is a DIFFERENT shape — even if it happens to contain
all the same fields CandidateHero actually reads, TypeScript treats them
as unrelated types and will refuse to compile the code that passes a
`DummyDeckProfile` into a component expecting a `DummyFemaleProfile`.

The PRD already sanctioned an escape hatch for the OTHER reuse case
(ProfileScrollView) with a documented cast: `deck as unknown as
UserProfile & DummyOverlay`. But it forgot to say the same thing about
CandidateHero. The developer will hit the compile error and have to
either invent a fix on the fly or pause and ask.

ANALOGY

You bought a universal power adapter last year that says "fits any device
with a Type-C USB port". This year you buy a laptop that has a Type-C USB
port. You plug it in — but the adapter has an extra check on the label
that says "only fits the Model X laptop we bought last year". The shape
of the plug is the same. The check on the label is what's rejecting you.
Either widen the label, or explicitly say "yes, we know it's not a Model X
but plug it in anyway".

FIX OPTIONS

  (a) Cast at the DeckCard boundary — same pattern the PRD already uses
      for ProfileScrollView. One line: `<CandidateHero profile={deck as
      unknown as DummyFemaleProfile} />`. Add a code comment explaining
      the cast is intentional. This is my recommendation. Zero churn
      and consistent with the sibling case.

  (b) Widen CandidateHero's prop type. Extract a narrower structural
      interface (a "CandidateHeroProfile" = just the 8-or-so fields it
      actually reads) and change the prop type. More correct long-term
      but requires editing a phase-12 component and re-verifying its
      tests.

  (c) Make DummyDeckProfile extend DummyFemaleProfile (or vice-versa).
      Couples the two types together permanently — bad, because when the
      real backend ships and DummyDeckProfile is derived from the
      backend's response, DummyFemaleProfile would need to change with
      it, which is a phase-13/phase-12 coupling we don't want.

  ANSWER: go with option b

SHARPEN 1 — What does the unread-notification dot on the bell icon
            actually mean?
================================================================================

WHAT THE PRD SAYS (story 13.3)

Keep the phase-12 HeaderBar (filter left, bell right). The little red dot
on the bell is "derived from the currently visible deck profile's
`has_unread_notifications`".

WHY IT'S WORTH LOCKING DOWN

Every notification bell in every app in the world means "YOU have unread
notifications" — the current user's own. Not "the person you're LOOKING at
has unread notifications". That would be like Instagram showing you the
unread-DM dot only when you're viewing Cristiano Ronaldo's profile
(because Ronaldo has a lot of unread DMs). Meaningless from the current
user's perspective.

Phase 12 already did this cheat because there was only one candidate
(Aisha) and the bell dot came from her JSON. It "worked" because the
screen never changed. Phase 13 introduces a deck of 5 cards, so the dot
will now flicker on/off as the user swipes through the cards. That will
look like a bug to any tester.

ANALOGY

Imagine your car's fuel-warning light is wired to the fuel gauge of the
car parked next to you at every red light. Every time you pull up
alongside a different car, the light comes on or goes off. That's what
we're building.

FIX OPTIONS

  (a) Read the dot from the current user (dummyprofile.__dummy_display_
      only?.has_unread_notifications) instead. One-line change. My
      recommendation.

  (b) Keep as-written and accept the flicker as a mock-only fudge; add a
      line to the phase-13 teardown list in context.md so nobody debugs
      it later.

  (c) Hardcode it to `false` for phase 13 and revisit when real
      notifications ship (phase 19).

  ANSWER: Go with option a


================================================================================
SHARPEN 2 — What does the Like button ACTUALLY do internally? Does
            it create a real pending request, or is it just theatre?
================================================================================

WHAT THE PRD SAYS (story 13.3)

Like → advance the deck to the next card + Snackbar "Friend request sent".

That's the entire acceptance criterion for the Like button. No mention
of writing to the FriendshipProvider, no mention of creating a
`dummyrequests.json` entry, no mention of any persistent state change.

WHY IT'S WORTH LOCKING DOWN

There are two coherent interpretations and they lead to different code:

  Interpretation A — "Like is theatre". The snackbar says "sent" but
    nothing is written anywhere. The current user could swipe Like on
    Aisha and then, one second later, someone from the outside sends
    Aisha a message on WhatsApp — Aisha has no idea our user liked her.
    Real backend request-create is a phase-15 story. Phase 13 just
    displays the message to give the user a satisfying "I did something"
    feel while all state is still mock.

  Interpretation B — "Like creates a pending request in the
    OTHER direction". Now the deck user's Like adds a record to the
    OTHER user's incoming requests. But we don't model that in phase 13
    (dummyrequests.json only tracks incoming to OUR user, and we don't
    have a "the deck user's outgoing requests" model).

I believe the PRD intends interpretation A (mock theatre), and phase 15
is where real request-write lands. But we should say so explicitly on
the story so the developer doesn't add half-baked provider writes.


ANALOGY

You press the "Call for service" button on a train seat. The button
flashes a green light saying "Attendant notified". Interpretation A:
the button is not actually wired to anything, but the light makes you
feel heard. Interpretation B: the button DID actually page an
attendant. If it's A, no problem. If it's B and the wiring is
mis-installed, you sit there confused when nobody comes.

FIX OPTIONS

  (a) Confirm interpretation A. Add an AC to story 13.3: "Like does
      NOT write to FriendshipProvider. Real pending-request creation
      ships in phase 15." My recommendation.

  (b) Confirm interpretation B. Extend the FriendshipProvider to track
      an outgoing-request list, extend Story 13.3 with the write, and
      show the Like's target as a pending request in the Explore
      Requests tab of a DIFFERENT test user account. Big scope creep;
      not recommended for phase 13.
  

  
ANSWER: Go with option A for now, this is just to mock, later we will change this

SHARPEN 3 — What does the deck-exhausted state look like?
            Hide the action bar, or grey it out?
================================================================================

WHAT THE PRD SAYS (story 13.3)

When the user reaches the end of the deck (index >= 5), the scroll
content is replaced by an EmptyState. The action bar (X / Undo / Star /
Check) either "hides in the exhausted state (or its buttons become
disabled — decide at brainstorm)".

WHY IT'S WORTH LOCKING DOWN

Two coherent UX affordances:

  Hide entirely — no buttons at all. Reads as "there's nothing here
    for you to do". Matches the EmptyState's message.

  Show but disabled — buttons visible but greyed out. Reads as
    "the buttons are broken right now". Confusing.

ANALOGY

If a shop is closed for the night, do they turn the neon signs off
entirely, or leave them on but dimmed? "Off entirely" reads as "come
back later, we're closed". "On but dim" reads as "the electrician needs
to be called".

FIX OPTIONS

  (a) Hide entirely. My recommendation.

  (b) Show but disabled.

  (c) Hide only the X / Star / Check but keep Undo visible so the user
      can step BACK into the deck (rewind their last swipe). More
      complex UX but genuinely useful — you might want to un-Dislike
      the last card you swiped away.

ANSWER: go with option A


================================================================================
SHARPEN 4 — When the user swipes to the next deck card, does the tab
            bar and the action bar snap back into view?
================================================================================

WHAT THE PRD SAYS (story 13.3)

"Scroll position resets to 0 whenever `currentDeckIndex` changes."

WHY IT'S WORTH LOCKING DOWN

In phase 12 we wired the bottom tab bar and the round action bar to
collapse (translate down and fade out) when the user scrolls DOWN, and
snap back into view when they scroll up. That collapse is driven by a
shared Reanimated value called `marriageTabBarHidden`.

When the user has scrolled halfway down Aisha's profile (tab bar
collapsed) and hits Dislike to advance to the next card, the scroll
position resets to 0 (good). BUT the `marriageTabBarHidden` shared
value is still stuck at 1 (fully collapsed). So the new card renders
at the top of its scroll, but the tab bar is still off-screen.

The user has to manually scroll DOWN a bit and then UP again to make
the tab bar reappear. Not obvious.

ANALOGY

You're reading a magazine. As you scroll down a page, the header of
the magazine slides up out of view (nice, gives you more reading room).
You flip to the next page and start at the top of the page — but the
header is still hidden. You have to scroll partway down and back up
just to make the magazine's title reappear. Weird.

FIX OPTIONS

  (a) Add to Story 13.3 AC: "On deck advance/undo, reset
      marriageTabBarHidden.value to 0 with a smooth withTiming
      animation, so the tab bar and action bar spring back into view
      alongside the scroll reset." My recommendation.

  (b) Do nothing and let the user scroll to bring the tab bar back.
      Consistent-but-jarring.

ANSWER: Go with option a

SHARPEN 5 — Does the Requests-tab full-profile view leak the target
            user's phone number BEFORE the current user accepts them?
================================================================================

WHAT THE PRD SAYS (story 13.4)

The OtherProfileScreen for source='request' shows the same
ProfileScrollView as source='friend'. The difference is only the header
(back-arrow only) and the extra Accept/Decline bar. The ProfileScrollView
already renders a ContactActionsSection at the bottom that shows the
target user's phone number and a share button.

WHY IT'S WORTH LOCKING DOWN

Consider Qurat sending our user a friend request. Our user opens Qurat's
profile from the Requests tab and — without accepting anything — can
already see Qurat's phone number and copy/share it. In a real matrimonial
app this is a genuine privacy leak: contact info is generally revealed
AFTER two users mutually accept. Once you've DECLINED, you've had access
to her phone number anyway.

For friends (accepted), showing the phone is fine — that's what a friends
list is for.

ANALOGY

A dating app has a "someone likes you" screen. You can see their profile
photo and their bio. But their phone number is hidden behind a "match to
reveal" gate. That gate is what protects users who haven't matched from
handing out their contact info too early.

The PRD is currently unlocking the gate on both the "match" side AND the
"pending request" side.

FIX OPTIONS

  (a) Add an optional `contactVisible?: boolean` prop to
      ProfileScrollView (defaults to true so phase-12 callers don't
      break). OtherProfileScreen passes `contactVisible={source ===
      'friend'}`. My recommendation — closes the leak, minimal change.

  (b) Accept the leak as mock-only. Add a note to the phase-13 teardown
      list in context.md. The real backend will presumably not return
      Qurat's phone number in the request-view response anyway.

  (c) Split ContactActionsSection into ContactRow (phone) and
      ContactActions (Share/Favourite/Block/Report), so OtherProfileScreen
      can hide just the ContactRow while keeping the share button
      visible. Cleaner but more code.

ANSWER: Go with option A

NOTE 1 — Row-body-vs-buttons touch conflict in Explore Requests list.
================================================================================

WHAT THE PRD SAYS (story 13.5)

Requests list row: thumbnail + name + subtitle on the left, Accept and
Decline buttons on the right. "Row-body press (i.e. everything except
the two buttons) → navigate to OtherProfileScreen. Button press → run
the button's own action."

WHY IT'S WORTH FLAGGING

React Native's default touch propagation means if the whole row is
wrapped in a TouchableArea, tapping Accept ALSO fires the row press —
so the user simultaneously navigates AND accepts. Devs often solve this
with stopPropagation in the button handler, which works but is easy to
forget.

The clean structure is: TouchableArea wraps ONLY the left column
(thumbnail + name/subtitle). The two buttons sit in a SIBLING Row
outside the touchable. Then there's no conflict at all.

Non-blocking. Just a hint to save the developer half a debugging
session.

NOTE 2 — Cold-start reset of the FriendshipProvider is EXPECTED behavior,
         not a bug.
================================================================================

WHAT THE PRD SAYS (story 13.2)

FriendshipProvider is in-memory only for phase 13. State resets on
every cold start.

WHY IT'S WORTH FLAGGING

If you Accept Qurat during a QA session and then close the app and
reopen it, Qurat's request will come back and Mehvish will be the only
friend again. This is EXPECTED. It's marked TODO(mock-only). Real
persistence ships in phase 15.

Non-blocking. Just so nobody files it as a bug during QA.

================================================================================
NOTE 4 — Story 13.4 leaves the choice of "reusable BackHeaderBar
         component" vs "inline header" up to the implementer.

================================================================================

WHAT THE PRD SAYS (story 13.4)

"Either a new BackHeaderBar component in features/profile/components/
OR an inline header rendered directly in the screen. Whichever pattern
is chosen, the header is visually consistent with the phase-12
HeaderBar."

WHY IT'S WORTH FLAGGING

If we build a reusable BackHeaderBar now, phases 15 (friend-requests
standalone), 17 (chat room), and 18 (blocks) can all reuse it. If we
inline it now, three future phases will each build their own or
retrofit the inline one out.

Non-blocking. My recommendation is to build the reusable component
now, but it's a small enough call that "inline is fine" is a valid
answer too.
