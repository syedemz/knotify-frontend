================================================================================
PHASE 5 — CONCERNS EXPLAINED IN PLAIN ENGLISH
================================================================================

Phase 5 builds pages 12, 13, and 14 of the onboarding wizard:
  - Page 12: pick your education level (5 choices)
  - Page 13: fill in details based on that level (school name, year, etc.)
  - Page 14: "second checkpoint" — save progress + ask for notification and
             location permissions

I audited the plan against the code we actually have today and found 15
issues. They range from "the app will literally crash" to "small wording
cleanups." I've numbered them and rated severity. For each one you get
three sections:

  WHAT THE PLAN SAYS  — the exact instruction in the PRD
  WHY IT MATTERS      — what will happen if we don't decide
  YOUR CHOICES        — the options I see, with the recommended one marked

Just tell me the number and letter for each one (e.g., "1: A, 2: B, 3: A")
and I'll update the plan accordingly.

BLOCKERS — things that would make the app crash or the plan not compile
================================================================================

--------------------------------------------------------------------------------
ISSUE 1 — SEVERITY: BLOCKER
    "The plan asks for location permission but the phone doesn't know how"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS:
    Story 5.3 says to create a helper called `requestLocationPermission()`
    using an Expo library called `expo-location`.

WHY IT MATTERS:
    Analogy — it's like the plan says "the ambulance will use its siren,"
    but the ambulance doesn't have a siren installed. `expo-location` is
    not in our project's list of installed packages (`package.json`). If
    the developer writes the code as-is, the app will build fine in unit
    tests (they mock the module) but crash the first time a real phone
    tries to run it, because the native code for asking iOS/Android for
    GPS access isn't there.

    Also, iOS and Android both require you to declare, in an app config
    file, WHY you want location — a short user-facing sentence like
    "Knotify uses your location to show nearby matches." Without that,
    Apple's App Store review will reject the build.

YOUR CHOICES:
    A) (RECOMMENDED) Add an explicit sub-task to story 5.3:
       "Run `npx expo install expo-location`. Add
       NSLocationWhenInUseUsageDescription (iOS) and ACCESS_FINE_LOCATION
       + ACCESS_COARSE_LOCATION (Android) to `app.json` / `app.config.ts`
       with the copy: '<your one-sentence justification>'." Then proceed.
    B) Skip the location permission entirely for now — only ask for
       notification permission on page 14. Location would be requested
       later, from wherever it's actually first used.
    C) Ask me for the exact justification copy right now so we bake it
       into the plan.

    If you pick A, I'll need one sentence of justification copy from you
    for the OS prompt. If you don't have one in mind, a safe default is:
    "Knotify uses your approximate location to show you compatible
    matches nearby."

    ANSWER: Option A with the recommended safe default "Knotify uses your approximate location to show you compatible
    matches nearby"

ISSUE 2 — SEVERITY: BLOCKER
    "The plan tells us to build something that already exists"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS:
    Story 5.3 says: create `src/services/permissions/index.ts` with a
    function `requestNotificationPermission()` that wraps
    `expo-notifications`.

WHY IT MATTERS:
    Analogy — it's like the plan says "install a doorbell" but there's
    already a working doorbell around the back of the house that nobody
    told the planner about. In our code, `src/services/push/expoPush.ts`
    already has a private function called EXACTLY `requestNotificationPermission`
    doing exactly what the plan asks for. It's used to register the phone
    for push notifications.

    If the developer just follows the plan blindly, we'll end up with
    TWO functions with the same name doing the same thing. Six months
    from now, someone will change one and forget the other, and we'll
    get "notifications work sometimes" bugs.

YOUR CHOICES:
    A) (RECOMMENDED) Extract the existing function out of `expoPush.ts`
       and move it into the new `services/permissions/index.ts`. Then
       have `expoPush.ts` import it. One implementation, both callers
       share it. The PRD should say this explicitly so the developer
       doesn't accidentally duplicate.
    B) Leave the existing one alone and put a separate copy in
       `services/permissions/index.ts`. Two copies, guaranteed to drift.
       (Do not pick this.)
    C) Put the notification helper in `expoPush.ts` and have the new
       `services/permissions/index.ts` re-export it. Backwards direction
       — `permissions` is the lower-level building block; making it
       depend on `push` is inside-out.

    ANSWER: Option A

ISSUE 3 — SEVERITY: BLOCKER
    "The plan writes to draft fields that have different names than what's
     actually in the draft schema"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS:
    Story 5.3 says both permission results are "written to draft
    (`notification_permission_status`, `location_permission_status`)."

WHY IT MATTERS:
    Analogy — imagine writing a check to "John Smith" when the account
    is actually under "J. Smith". The check bounces. Same idea here in
    two ways:

    (a) NAMING STYLE: The plan uses snake_case
        (`notification_permission_status`) but the draft file defines
        these fields in camelCase (`notificationPermissionStatus`). One
        of them is wrong.

    (b) LOCATION IN THE SHAPE: The plan implies these live INSIDE
        `draft.fields.*` (where all the profile-column stuff lives). But
        the actual schema puts them at the TOP LEVEL of the draft —
        siblings of `fields`, `siblings`, `photoPreviewUris`. Different
        location, different setter.

    On top of that, the draft hook (`useOnboardingDraft`) only exposes
    ONE top-level setter today (`setSiblings`). Story 5.3 needs new
    setters (something like `setNotificationPermissionStatus`) that
    don't exist yet. The plan doesn't mention this — it's a hidden
    sub-task that would surprise the developer mid-story.

YOUR CHOICES:
    A) (RECOMMENDED) Update the PRD to use the EXISTING camelCase names
       (`notificationPermissionStatus`, `locationPermissionStatus`) and
       add an explicit sub-task: "Extend `useOnboardingDraft` with two
       new top-level setters modeled on `setSiblings`:
       `setNotificationPermissionStatus(status)` and
       `setLocationPermissionStatus(status)`."
    B) Rename the draft-schema fields to snake_case to match the PRD.
       (More churn — snake_case is what backend/DB uses, camelCase is
       what all our JS/TS code uses. Client-side draft fields staying
       camelCase is more consistent with the rest of the codebase.)

ANSWER: Option A

--------------------------------------------------------------------------------
ISSUE 4 — SEVERITY: MEDIUM
    "Story 5.1 has an acceptance criterion that only story 5.2 can satisfy"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS:
    Story 5.1 acceptance criterion 3 reads: "Back-navigation from page 13
    to page 12 is supported; changing the selection triggers page 13's
    re-mount reconciliation (implemented in 5.2)."

WHY IT MATTERS:
    Analogy — imagine a job description that says "You will hire your own
    boss." That's a contradiction — you can't be tested against something
    that requires another role to exist.

    Story 5.1 is Page 12 only. The "reconciliation" (auto-clearing
    obsolete fields when the user downgrades their education level) lives
    in Page 13, which is story 5.2. So story 5.1 can't be tested against
    this criterion — it would need story 5.2's code, which by definition
    doesn't exist yet when we're building story 5.1.

    It's not a bug per se; it's a testability issue. The story appears
    to depend on 5.2, but `depends_on: []` (nothing) is what the PRD
    declares.

YOUR CHOICES:
    A) (RECOMMENDED) Rephrase 5.1's AC 3 to only cover what 5.1 can
       actually verify: "Back-navigation from page 13 to page 12 is
       supported (the nav wiring works — no navigator errors, the
       previous selection is still shown)." Move the reconciliation
       clause into 5.2's AC set (it's basically already there as 5.2
       AC 4).
    B) Delete AC 3 from 5.1 entirely; 5.2's AC 4 covers the same idea.

ANSWER: Option A

STORY 5.2 (Page 13 — dynamic education-details form) — the biggest story
================================================================================

--------------------------------------------------------------------------------
ISSUE 7 — SEVERITY: MEDIUM
    "One acceptance criterion is doing the work of three"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS:
    Story 5.2 AC 5: "Screen wiring test covers each of the 5 branch
    matrix rows including auto-default of hidden fields, the back-nav
    downgrade reset, and Continue navigation to
    `Page14SecondCheckpointScreen`."

WHY IT MATTERS:
    Analogy — one test that says "check the engine, check the tires,
    and check the brakes." If any one fails, you don't know which. And
    if all three are jammed into one test function, it's harder to fix
    the failing part.

    Better practice: one AC per behavior, one test per AC. Easier to
    read, easier to debug when something breaks, easier to see coverage
    gaps.

YOUR CHOICES:
    A) (RECOMMENDED) Split AC 5 into three bullets:
       - For each of the 5 education-level values, the correct field
         set renders and hidden fields are auto-defaulted to their
         sentinels in the draft.
       - Back-navigating to page 12 and picking a lesser level force-
         resets the now-irrelevant fields to defaults before page 13
         re-mounts.
       - Continue is only enabled when every visible field validates;
         tapping it navigates to `Page14SecondCheckpointScreen`.
    B) Leave as one bullet — the test will still be written, it'll just
       be one big test.

ANSWER: Option A

ISSUE 14 — SEVERITY: MEDIUM
    "What happens when only ONE of the two permissions is granted?"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS:
    "On resume when both permissions are already granted, the screen
    shows a plain Continue button without re-prompting."

WHY IT MATTERS:
    Analogy — the plan tells you what to do when the light is green
    (both granted) and implies what to do when it's red (both denied),
    but says nothing about yellow (one granted, one denied). There are
    actually 6 combinations, and iOS specifically will NOT let you
    re-prompt once a user has denied — the OS returns 'denied'
    immediately and shows nothing.

    Combinations to cover:
      - Both granted → plain Continue ✓ (in plan)
      - Both null (fresh) → show "Enable Notifications" flow ✓ (in plan)
      - Notif denied, location null → ??
      - Notif null, location denied → ??
      - Notif denied, location denied → ??
      - Notif granted, location denied → ??

    Simplest rule: if EITHER permission is 'denied' with `canAskAgain:
    false`, show plain Continue (can't do anything anyway — user must
    go to Settings). If either is null / undetermined, show the "Enable
    Notifications" flow.

YOUR CHOICES:
    A) (RECOMMENDED) Add explicit rule: "On mount, if either permission
       has status `null` or `undetermined`, show the 'Enable
       Notifications' flow (which sequentially prompts for both). If
       both statuses are terminal (`granted` OR `denied` with
       `canAskAgain: false`), show plain Continue. Persist the observed
       status on every mount."
    B) Simpler rule: "Show 'Enable Notifications' flow unless BOTH are
       granted. Prompting a denied permission is a no-op on iOS and
       returns 'denied' again — that's acceptable." (Fewer edge cases,
       but users may see the button not do anything on re-tap.)
    C) Even simpler: never re-prompt. If we've asked before, show plain
       Continue always. (Only ask once, first mount.)

ANSWER: Option A
