CONCERN #1 — "Do you have children?" and "Willing to move abroad?" want to
             save the word "YES" or "NO", but the backend expects true/false
             (BLOCKS THE BUILD)
--------------------------------------------------------------------------------

What's happening:

On page 23, if the user picks "Divorced" or "Widowed", we ask "Do you have
children?" and offer two buttons: YES / NO. On page 24, we ask "Would you be
willing to move abroad after marriage?", again with YES / NO.

The PRD says: when the user taps YES, save the text "YES" into the field
called `has_children` (page 23) or `move_abroad` (page 24). When they tap NO,
save the text "NO".

But if I go read the file that defines what shape those fields have, they are
declared as true/false fields — not text fields. So writing the word "YES"
into a true/false slot is like trying to slide a square peg into a round hole.
TypeScript (the compiler) will refuse to build the app.

Analogy:

Imagine a form at the DMV that has a checkbox labeled "Are you an organ
donor?" The checkbox can only be checked or unchecked — it's a yes/no
switch. The PRD is telling the developer to write the actual English letters
"Y-E-S" onto the checkbox instead of just checking it. The checkbox has no
place for letters. The form rejects it.

Meanwhile in phase 7 (parents page, "Is your father retired?"), a similar
YES/NO question worked fine because the `father_retired` field was
specifically declared as a text field — so writing "YES" and "NO" as text was
fine there. Two fields, same question style, different underlying type.
That's the inconsistency biting us here.

Options:

(a) COERCE AT SAVE TIME (recommended — smallest change). When the user taps
    YES on the children question, save `true` into `has_children`. When they
    tap NO, save `false`. Same for `move_abroad`. On page revisit, we read
    the boolean back and light up the correct button. The user still sees
    YES/NO on screen; only the internal storage changes.

(b) WIDEN THE FIELD TYPES. Change `has_children` and `move_abroad` in
    `UserProfile.ts` from boolean to text, matching the phase-7 precedent.
    This is bigger — it touches other files, other tests, and might
    contradict what the backend schema actually stores. Only pick this if
    you know the backend stores text and the type file is currently wrong.

(c) DO BOTH — pick option (a) at the code level AND amend the PRD wording so
    it no longer says the misleading `has_children='NO'`. Same effort as (a)
    but leaves cleaner documentation.

What's happening:

pasta. The waiter needs to erase it. The PRD says "erase it before serving
the food" but uses the phrase "when you back-navigate to the menu" which
sounds like you left the restaurant, came back, and reordered.

Also missing: the rule only mentions Divorced+Yes → Never Married. What
about Widowed+Yes → Never Married? What about Divorced+No → Never Married?
Any change TO Never Married should wipe the children answer.

    previously selected Divorced or Widowed on this page — regardless of

CONCERN #5 — Auto-advance might re-fire when the user hits the back button
--------------------------------------------------------------------------------

What's happening:

Every page in phase 8 auto-advances the moment the user makes a selection.
That's fine on first visit. But what about back-navigation? Say the user is
on page 22 and hits back to go to page 21. The draft still has their
previous religious level answer saved. If we're not careful, page 21 will
notice "oh, there's a value in `religious_level`" and immediately
auto-advance right back to page 22. The back button becomes a rubber band —
you can't actually go back.

Analogy:

A revolving door with a motion sensor: as soon as someone walks in, it
spins them forward into the building. Great for entry. But if someone
inside the building tries to walk out through the same door, the sensor
sees them and spins them back INTO the building. They can never leave.

Options:

(a) TAP-TRIGGERED ONLY (recommended). Auto-advance fires only when the user
    physically taps an option — not when the screen mounts with a pre-filled
    value. This is what phase 7 already does; it's the standard pattern.
    Just needs to be called out explicitly in the subagent brief so the
    subagent doesn't put the auto-advance inside a `useEffect` that watches
    the draft.

(b) TAP-TRIGGERED, BUT PRESELECT VISIBLE. Same as (a), plus on re-visit the
    previously-chosen option is visually highlighted so the user can see
    where they left off. This is worth doing regardless.

(No option is really wrong here — I just want to guarantee the subagent
doesn't accidentally build the rubber-band version.)
