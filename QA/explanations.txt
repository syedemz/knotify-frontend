================================================================================
PHASE 14 BRAINSTORM — LAYMAN EXPLANATION OF THE PROBLEMS FOUND
================================================================================

Before I dispatch anyone to write phase-14 code, I re-read the PRD and
cross-checked every claim in it against the code that already shipped in
phases 12 and 13. I found 3 blockers (things that will trip the developer
on day one), 2 medium sharpens, and 3 small notes. Each item below is
written plainly with an analogy where useful. At the end of each item are
the fix options so you can pick one — or write your own.

Vocabulary refresher (skip if you already know it):

  - "PRD"        = the phase-14 plan file at
                   implementationplan/phase-14-bookmarks.md
  - "story"      = one numbered task inside that plan (14.1, 14.2, 14.3, 14.4)
  - "AC"         = "acceptance criteria" — the checklist inside each story
                   that says "this story is done when X and Y and Z are true"
  - "shared value" = a Reanimated primitive (imagine a single variable that
                   both React and the animation runtime can read/write at
                   60 fps). We use it to animate the bottom tab bar down
                   when the user scrolls.
  - "route type" = a TypeScript declaration saying "the ExploreStack has
                   these screens, and each takes these params". If a screen
                   is missing from the type, TS refuses to compile any call
                   that navigates to it.
  - "provider"   = a React context holding shared state. We already have
                   AuthProvider, FriendshipProvider, etc. Phase 14 adds
                   BookmarksProvider.
  - "AsyncStorage" = React Native's plain key/value disk store (like
                   localStorage in a browser). Bookmarks live here so
                   they survive app restarts.
  - "expo module" = a native library that ships with Expo. Adding one
                   requires `npx expo install <name>` (which patches
                   package.json AND regenerates the native side of the
                   dev-client). A plain `npm install` is NOT enough.

BLOCKER 1 — The PRD tells the developer to import a file that doesn't
            exist under that name anymore.
================================================================================

WHAT THE PRD SAYS (story 14.4)

The new BookmarkDeckViewScreen needs a "floating add-request button" (a
round button that sits above the bottom tab bar). When the user scrolls
down the deck card, the tab bar slides off-screen and the button rides
with it. The animation is driven by a single Reanimated shared value —
one variable everyone reads/writes to keep every screen's collapse in
sync.

Story 14.4 AC says: "pass `marriageTabBarHidden` from
`src/features/landing/shared/marriageTabBarHidden.ts`".

WHY IT'S A PROBLEM

That file has been renamed and moved since the PRD was written.

  - Old name:  marriageTabBarHidden
  - New name:  tabBarHidden
  - Old path:  src/features/landing/shared/marriageTabBarHidden.ts
  - New path:  src/state/ui/tabBarHidden.ts

The rename happened during phase 13 — once the Explore tab (not just
Marriage) started writing to the same shared value, the "marriage" prefix
stopped describing the reality. The JSDoc at the top of tabBarHidden.ts
explains the rename in its own words.

If the developer copy-pastes the AC verbatim, they will chase down a file
that no longer exists, and either invent a new one (worst outcome — two
shared values, out of sync) or pause to ask.

ANALOGY

Imagine your PRD says "call Mrs. Robertson at extension 4501". But
Mrs. Robertson got married last year and changed her surname to Nakamura
and got transferred to extension 5610. The instructions LOOK right, but
if you dial the number in the PRD you either get a dead line or —
worse — you get a totally unrelated person named Robertson who now
answers on that line.

FIX OPTIONS

  (a) Update the PRD in three places:
      - Story 14.4 AC: change to "pass `tabBarHidden` from
        `src/state/ui/tabBarHidden.ts`".
      - Story 14.4 notes block: swap `marriageTabBarHidden` for
        `tabBarHidden`.
      - context_summary: same swap.
      My recommendation. Zero code impact, keeps the PRD accurate.

  (b) Leave the PRD as-is and trust the subagent to figure it out. The
      grep will succeed on the file's own JSDoc which explains the
      rename, so a smart subagent can bridge it. But this trades
      certainty for cleverness and creates a risk of a bad guess.

  (c) Rename `tabBarHidden` BACK to `marriageTabBarHidden`. Nonsensical
      — the rename was correct, the PRD is out of date.

ANSWER: yes go with option a

BLOCKER 2 — The PRD invents a label-key namespace that the codebase
            doesn't use.
================================================================================

WHAT THE PRD SAYS (story 14.3)

The Explore screen already has two tabs (Friends and Requests) with
label keys. Story 14.3 adds a third tab (Bookmarks). The AC says:

  New label: `explore.tabs.bookmarks`
  Sits alongside existing keys `explore.tabs.friends` and
  `explore.tabs.requests`.

WHY IT'S A PROBLEM

Those two "existing" keys don't exist. The actual keys today are
`explore.friends` and `explore.requests` — no `.tabs.` in the middle.
If we add `explore.tabs.bookmarks`, we end up with a Frankenstein
namespace where two tabs live under `explore.*` and the third one lives
under `explore.tabs.*`. Anyone opening `labels.en.json` later will
assume the pattern is inconsistent and either try to "fix" it (touching
phase-13 code we said not to touch) or copy the wrong prefix in phase 15
and beyond.

ANALOGY

Every apartment on your floor is numbered "4-A", "4-B", "4-C". You buy
the empty apartment next door and the landlord tells you it's "4-Wing-D".
Now every delivery driver, every friend, every emergency responder has
to be told "yes, we're on floor 4 but the addressing scheme changes
just at our door". It works. It's ugly.

FIX OPTIONS

  (a) Use `explore.bookmarks` for the new key. Matches the existing
      convention exactly. Also fix the PRD's false claim about
      `.tabs.friends` / `.tabs.requests` existing. My recommendation.

  (b) Rename `explore.friends` → `explore.tabs.friends` and
      `explore.requests` → `explore.tabs.requests` too, so all three
      match the PRD's proposed namespace. Correct if you think `.tabs.`
      is a better structure long-term, but it touches phase-13 code
      (the PRD said not to). Larger churn.

  (c) Ship as-is with the inconsistent naming and add a cleanup story
      to a future refactor phase. Delays the mess, doesn't avoid it.

ANSWER: okay sounds right, use option a

BLOCKER 3 — Story 14.3 uses a library we haven't installed yet, and
            the install command is different from a normal npm install.
================================================================================

WHAT THE PRD SAYS (story 14.3)

Each BookmarkCard shows a photo with the user's name and details
overlaid at the bottom. To keep the text readable no matter what the
photo looks like, we add a dark-to-transparent gradient across the
bottom of the card. The PRD says use `expo-linear-gradient` for that.

The PRD notes acknowledge this: "If it is not currently in package.json,
it is an Expo module and can be installed via `npx expo install
expo-linear-gradient`."

WHY IT'S A PROBLEM

The library is NOT currently in package.json. And this is an expo module,
which means `npm install` is not the right command — you need
`npx expo install` because it also patches the native side of the
dev-client, then a Metro restart. If a subagent does a plain
`npm install expo-linear-gradient` (a very common mistake), the JS side
works but the native module isn't linked and you get a red-screen
runtime error the first time a BookmarkCard renders.

The PRD flags this in the notes block, but not as a hard AC. Notes get
skimmed. ACs get followed.

ANALOGY

The recipe says "add a pinch of saffron", and mentions in the margin
"we don't currently stock saffron — pick some up on the way to work".
The chef gets busy, skims the margin note, and starts cooking without
saffron. The dish comes out wrong at the last step.

FIX OPTIONS

  (a) Promote the install line to a first-class AC on story 14.3:
      "Run `npx expo install expo-linear-gradient` and verify it appears
      in package.json before writing the LinearGradient import."
      My recommendation. Zero-cost sharpen.

  (b) Leave in the notes and trust the subagent. Cheaper on PRD editing,
      more risk on execution.

  (c) Swap out the gradient scrim for a plain semi-opaque
      `View style={{ backgroundColor: 'rgba(0,0,0,0.55)' }}` and skip
      the dependency entirely. Loses the gradient (which is what makes
      text over an arbitrary photo look polished) but avoids the
      install step altogether.

ANSWER: let us try option c, if i dont like it then we can use the gradient later

SHARPEN 1 — Story 14.3 tries to navigate to a screen that only exists
            after story 14.4 lands. TypeScript will refuse to compile it.
================================================================================

WHAT THE PRD SAYS (stories 14.3 and 14.4)

Story 14.3 builds the Bookmarks grid on ExploreHomeScreen. Each card in
the grid, when tapped, is supposed to navigate to a new screen called
BookmarkDeckViewScreen using
`navigation.navigate('BookmarkDeckViewScreen', { userId })`.

Story 14.4 is the story that ACTUALLY adds BookmarkDeckViewScreen to
the ExploreStack — both the TypeScript type for the route AND the screen
component itself.

The stories are ordered so that 14.3 runs before 14.4 (which is correct
if you go by dependencies — 14.4 depends on 14.3 for the entry point).

WHY IT'S WORTH LOCKING DOWN

TypeScript enforces navigation types strictly. The moment story 14.3 tries
to call `navigation.navigate('BookmarkDeckViewScreen', ...)`, TS will say:
"there's no such screen in this stack". The build breaks. Tests won't
run because the file won't compile.

There are three ways out:

  (1) Do 14.4 before 14.3. But then 14.4 has nowhere to point its own
      "back button" entry point from (the Bookmarks tab), and TS on 14.4
      probably works but the acceptance criteria don't (you can't test
      "tapping a BookmarkCard opens BookmarkDeckViewScreen" until 14.3
      exists).

  (2) In story 14.3, register the route type AND stub in an empty
      placeholder screen (a component that just returns `null` or a "TODO
      14.4" text). Then story 14.4 replaces the placeholder with the
      real screen. Clean split — each story does one full thing.

  (3) Use a `// @ts-ignore` or cast the navigation call to `any` in
      story 14.3, and unmask it in 14.4. Cheap but ugly — the whole
      point of typed navigation is that you can't do this.

ANALOGY

You're building a house. The blueprints say "electrician wires up the
kitchen outlets first, then the plumber installs the sink". But the
kitchen outlets need to connect to the panel breaker that the plumber's
box actually houses. So the electrician has to either wait for the
plumber, install a temporary jumper wire, or fix the ordering. Doing
nothing means the electrician stops halfway through with a hot wire in
their hand.

FIX OPTIONS

  (a) Update story 14.3 AC to include: "Register
      `BookmarkDeckViewScreen: { userId: string }` on
      `ExploreStackParamList` in `src/navigation/types.ts`, and add a
      placeholder screen in `ExploreStack.tsx` that renders `null`.
      Story 14.4 replaces the placeholder with the real screen." My
      recommendation. Cleanest split, no TS suppressions, both stories
      remain testable.

  (b) Reorder: run 14.4 before 14.3. Awkward because 14.4's own tests
      ("tapping a bookmark card opens the screen") can't run until 14.3
      exists.

  (c) Allow a temporary `as any` cast in 14.3 with a `TODO(14.4)`
      comment. Works but every subagent-driven pattern like this
      eventually leaks into review.

ANSWER: okay go with option a

SHARPEN 2 — Story 14.1's description of "where to put the new provider
            in the tree" is wrong (harmless, but confusing to the
            subagent).
================================================================================

WHAT THE PRD SAYS (story 14.1)

The BookmarksProvider needs to sit in the React tree somewhere in App.tsx.
The PRD says:

  "Order: AuthProvider > OnboardingCompletionProvider > FriendshipProvider
   > BookmarksProvider > NavigationContainer."

WHY IT'S WORTH LOCKING DOWN

The insertion point (between FriendshipProvider and NavigationContainer)
is correct. But the described "order" is missing 5 outer providers that
already wrap those four:

  Actual tree:
    GestureHandlerRootView > SafeAreaProvider > ThemeProvider >
    LanguageProvider > QueryProvider > AuthProvider >
    OnboardingCompletionProvider > FriendshipProvider > NavigationContainer

The subagent will open App.tsx, see a much bigger tree than the PRD
described, and either (a) trust the PRD and try to delete the outer
providers ("the PRD says the top of the tree is AuthProvider — is the
tree wrong?") which would be a disaster, or (b) trust the file, insert
correctly, but pause to flag the mismatch.

Neither outcome is a code disaster — but option (a) is a real risk if
the subagent is over-eager.

ANALOGY

You tell a movers crew: "put the couch between the coffee table and
the TV stand". They arrive at the house and there's also a bookshelf,
a rug, three lamps, and a piano in that room. The instruction is still
followable — the couch's target position is unambiguous — but the movers
now have to decide whether YOU forgot the other furniture or the tenant
just added it after you wrote the note. If they take the note as
authoritative, they might move the piano out on their own initiative.

FIX OPTIONS

  (a) Trim story 14.1's AC to just: "insert BookmarksProvider between
      FriendshipProvider and NavigationContainer in App.tsx, keeping
      all existing outer providers untouched." My recommendation.
      Removes the misleading full-tree list, keeps the actionable
      instruction.

  (b) Rewrite the AC with the correct full 9-provider list. Accurate
      but verbose, and will go stale again the next time we add a
      provider.

  (c) Leave as-is. The subagent will probably read the code first
      anyway; only downside is a minor "wait, is this right?" pause.

ANSWER: okay go with option a

NOTE 1 — resolveDummyPhoto() can return undefined; the BookmarkCard AC
         doesn't say what to render in that case.
================================================================================

WHAT THE PRD SAYS (story 14.3)

Each BookmarkCard shows a background image via `resolveDummyPhoto()`.
The AC says use `photos[0]` if present, else `photo_url`. The overlay
text (name, age, job) sits on top of the image.

WHY IT'S WORTH FLAGGING

`resolveDummyPhoto()` returns `undefined` when the input is null or the
asset isn't registered. If a fixture ever has neither `photos[0]` nor
`photo_url` (in mock world this shouldn't happen, but the type allows
it), the card renders as: no background, dark scrim on nothing, white
text floating in mid-air with black scrim above it. Ugly but not broken.

Not a blocker. Just needs one line: "if `resolveDummyPhoto()` returns
`undefined`, render a solid `theme.colors.bg.surface` background under
the overlay". The subagent will likely add this on their own — but
making it explicit removes any lingering ambiguity.

ANSWER do the recommendation

NOTE 2 — SendRequestModal's testIDs were not confirmed by the audit;
         story 14.4's tests query by them.
================================================================================

WHAT THE PRD SAYS (story 14.4)

The tests for BookmarkDeckViewScreen use `getByTestId('send-request-card')`
and press `send-request-no-ask` to simulate the cancel flow. These IDs
come from the phase-13 SendRequestModal component.

WHY IT'S WORTH FLAGGING

The audit confirmed the modal's behavior (the `onCancel` after `onConfirmed`
timing, `SENDING_HOLD_MS = 1000`) but did not directly confirm the specific
testID strings. If the modal uses different strings — or no testIDs at
all — story 14.4's tests will fail on the wrong thing (querySelector,
not on any behavior).

Non-blocking. Just a heads-up for the 14.4 subagent: verify the testIDs
BEFORE writing the assertions. If they don't exist, either add them
(a passive change to SendRequestModal that changes no behavior) or query
by role/text instead.

NOTE 3 — AsyncStorage's jest mock is not currently registered anywhere.
================================================================================

WHAT THE PRD SAYS (story 14.1)

The AC says "use the standard `@react-native-async-storage/async-storage/
jest/async-storage-mock` preset. If not registered, add it — do NOT roll
a bespoke mock."

WHY IT'S WORTH FLAGGING

`jest.setup.ts` is currently empty (just a comment saying "no setup steps
required"). So the AC's second half ("if not registered, add it") is
what actually runs. The subagent will add one line
`jest.setup.ts`:

  jest.mock('@react-native-async-storage/async-storage', () =>
    require('@react-native-async-storage/async-storage/jest/async-storage-mock')
  );

Non-blocking. The AC already handles this. Flagging so you know that
"the mock is not currently registered" is a fact, not a surprise.
