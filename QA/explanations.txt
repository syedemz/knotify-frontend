Before I dispatch anyone to write phase-15 code, I re-read the PRD and
cross-checked every claim in it against the code that already shipped in
phases 12, 13, and 14. I found 2 blockers (things that will make the
developer's day-one work non-testable or crash the app), 5 medium
sharpens (things the developer will resolve one way or another during

Vocabulary refresher (skip if you already know it):

  - "PRD"        = the phase-15 plan file at
                   implementationplan/phase-15-friend-requests-and-chat-shell.md
  - "story"      = one numbered task inside that plan (15.1 through 15.7)
  - "AC"         = "acceptance criteria" — the checklist inside each story
                   that says "this story is done when X and Y and Z are true"
  - "provider"   = a React context holding shared state. We already have
                   AuthProvider, FriendshipProvider, BookmarksProvider, etc.
                   Phase 15 adds ChatProvider. Every screen in the app can
                   read from it without prop-drilling.
  - "AsyncStorage" = React Native's plain key/value disk store (like
                   localStorage in a browser). Sent friend requests and
                   chat history live here so they survive app restarts.
  - "modal"      = a dialog box that pops up over the current screen with
                   a dimmed backdrop behind it. Phase 15 adds two of them:
                   IncomingRequestModal (someone sent me a request) and
                   RequestAcceptedModal (someone accepted a request I sent).
  - "pendingToast" = a small state slot on FriendshipProvider that stores
                   a message to be shown as a snackbar the next time
                   ExploreHomeScreen focuses. It's how phase 13 solved
                   the "show a toast on a screen we just navigated away
                   from" problem.
  - "hook"       = a React function starting with `use` (useState,
                   useEffect, useChatHistory). React has strict rules:
                   hooks must be called at the top of a component, in
                   the same order every render, NEVER inside a loop or
                   inside a callback like FlatList's renderItem.
  - "FlatList"   = React Native's efficient list component. You give it
                   an array of data and a `renderItem` function that
                   returns JSX for one row. It only renders visible
                   rows for performance.
  - "testID"     = a string you attach to a component so tests can find
                   it. Like adding `id="submit-btn"` in HTML for tests
                   to hook into.
  - "DevTriggersPanel" = a temporary UI shown on the MyProfile Edit tab
                   in phase 15 with two buttons that manually pop the
                   two new modals for testing. The whole panel is
                   grep-tagged `TODO(mock-only)` and gets deleted in
                   phase 17 when real GraphQL subscriptions replace the
                   dev buttons.

BLOCKER 1 — The IncomingRequestModal can Accept/Decline a request, but
            no snackbar will ever fire on the screen you're actually
            looking at.
================================================================================

WHAT THE PRD SAYS (story 15.6)

The IncomingRequestModal is a dialog that pops up when someone sends me
a friend request. It shows the sender's avatar, name, and city, with
Accept and Decline buttons. The AC says:

  - The modal itself calls `acceptRequest(userId)` or `declineRequest(userId)`
    on FriendshipProvider.
  - Then the modal calls `onClose()` to disappear.
  - "Snackbar surfacing is the host's responsibility (via existing
    `FriendshipProvider.pendingToast` handoff or a local snackbar on the
    host screen)."
  - New labels are declared:
      friendRequests.incoming.acceptedToast   ("You are now friends with X")
      friendRequests.incoming.declinedToast   ("Request declined")

In phase 15 the trigger for the modal is a temporary button on the
MyProfileScreen Edit tab.

WHY THIS IS A PROBLEM

Think of `pendingToast` as a sticky note the FriendshipProvider leaves on
the fridge. Right now, only ExploreHomeScreen reads the fridge when it
walks into the kitchen (that is, when Explore is focused). Phase 13.4
built this pattern for a specific case: on OtherProfileScreen (which
lives inside the Explore tab), when you tap Decline, we `goBack()` you
to Explore immediately, and Explore reads the sticky note on focus and
shows the toast.

In phase 15, the modal opens on MyProfileScreen — which lives in the
Menu tab, NOT Explore. After you tap Accept:

  1. Modal calls `acceptRequest(userId)` — friendship state updated.  ✓
  2. Modal calls `onClose()` — modal disappears.                       ✓
  3. You're still on MyProfileScreen. ExploreHomeScreen never gets
     focused. The sticky note stays on the fridge, untouched.          ✗
  4. Toast never fires. Two labels (`acceptedToast`, `declinedToast`)
     exist but no code path renders them.

The AC is non-testable as written: it declares toast labels but points
at a mechanism (pendingToast) that doesn't reach the current screen.

ANALOGY

Imagine you finish a job at your desk and hit a "done" button. The
building's confetti-cannon system is only wired to fire in the lobby.
You're still upstairs at your desk. The confetti fires, but you don't
see it. The "confetti fired successfully" checkbox is technically
ticked, but the user experience missed the point entirely.

FIX OPTIONS

  (a) Local Snackbar on MyProfileScreen driven directly.
      Mount a Snackbar component on MyProfileScreen with local
      useState. When the modal fires Accept/Decline, the host passes
      the result back and MyProfileScreen shows its own snackbar. Skip
      pendingToast for this surface entirely.
      + Simple. Cleanly scoped to the screen the user is on.
      - MyProfileScreen grows a local snackbar; small state added.

  (b) Modal accepts callbacks (onAccept, onDecline) — host owns everything.
      Change the modal from "presentation-only that calls
      acceptRequest/declineRequest itself" to "presentation-only that
      fires onAccept(userId) / onDecline(userId) callbacks the host
      wired". Host then calls acceptRequest + shows local snackbar.
      This matches the shape of the RequestAcceptedModal in story 15.7,
      which uses onSayHi (already a host-owned callback).
      + Modal stays presentation-only. Consistent with 15.7. Host owns
        both the persistence AND the toast — one place, one flow.
      - 15.6 AC needs an edit: move the acceptRequest/declineRequest
        invocation from the modal into the host.

  (c) Broaden pendingToast consumers.
      Also mount a useEffect on MyProfileScreen that consumes
      pendingToast on focus. Same pattern as ExploreHomeScreen.
      + Reuses existing provider surface.
      - Two consumers means state churn is easier to double-consume or
        drop. Adds a subtle race with tab-switch focus events.

  MY RECOMMENDATION: (b). The modal is already declared "presentation-
  only" in the AC — passing user actions up through callbacks makes the
  modal a pure UI component and matches 15.7's shape.

  ANSWER: okay go with option b

BLOCKER 2 — The ChatListScreen would call a hook inside a FlatList's
            renderItem — React will throw at runtime.
================================================================================

WHAT THE PRD SAYS (story 15.4)

ChatListScreen shows a WhatsApp-style list of friends. Each row shows:

  - the friend's avatar (left)
  - name + last-message preview (middle)
  - timestamp (right)

The AC says: "Last-message preview is derived per-row from
`useChatHistory(friend.user_id).messages` — if messages array is
non-empty, show `messages[messages.length - 1].text`."

Which means: for every friend in the FlatList, we look up their chat
history via `useChatHistory(friendId)` and use the last message.

WHY THIS IS A PROBLEM

React has one very strict rule: hooks (any function starting with `use`)
must be called AT THE TOP LEVEL of a component, in the same order every
render. They CANNOT be called inside a callback that only runs on demand
— like FlatList's `renderItem`.

If you write:

    <FlatList
      data={friends}
      renderItem={({ item }) => {
        const { messages } = useChatHistory(item.user_id);  // ← ILLEGAL
        return <Row lastMessage={messages[messages.length-1]?.text} />;
      }}
    />

React will throw "Rendered more hooks than during the previous render"
or "Invalid hook call" the moment FlatList decides to render 3 rows
instead of 4 (when a friend goes offline, when the list scrolls, etc.).
It's a crash, not a warning.

ANALOGY

Imagine a restaurant where the chef can only take orders from a
specific position behind the counter — one at a time, in the order
customers walked in. If the chef starts taking orders while walking
around the dining room (from FlatList's renderItem), the whole system
falls apart because the kitchen loses track of which order came first.
React tracks hooks the same way: it counts hooks per component render
and expects the same count in the same order every single time.

FIX

Extract each row into its own component — `ChatListRow`. Then the hook
is at the top of ChatListRow, called exactly once per row instance:

    // src/features/chat/components/ChatListRow.tsx
    function ChatListRow({ friend, onPress }) {
      const { messages } = useChatHistory(friend.user_id);
      const last = messages[messages.length - 1];
      return <Row ... />;
    }

    // In ChatListScreen:
    <FlatList
      data={friends}
      renderItem={({ item }) => (
        <ChatListRow friend={item} onPress={() => nav(...)} />
      )}
    />

This is not a scope change — the same code, moved into a properly-
scoped component. But the AC doesn't spell it out, and a subagent
following the AC literally will inline the hook and hit the crash on
the first test run.

FIX OPTIONS

  (a) Add one line to 15.4 AC.
      Amend AC to say: "Row is a standalone component `ChatListRow` at
      `src/features/chat/components/ChatListRow.tsx` — the
      `useChatHistory` call lives at the top of that component, not
      inside `renderItem`."
      + Explicit, zero ambiguity. Subagent will not inline.
      - Requires a small PRD edit.

  (b) Leave the AC as-is, trust the subagent to extract the component.
      + No PRD edit.
      - Non-trivial risk the subagent inlines the hook and only catches
        the bug when tests fail. Wastes a dispatch cycle.

  MY RECOMMENDATION: (a). Non-negotiable React rule; better to lock it
  in the AC than let it become a "why is my test crashing" round-trip.

  ANSWER: okay go with option a, ofcourse it has to be a separate component, we have a rule remember, reusable components

SHARPEN 1 — The "cross-tab nav fixture test" in 15.5 doesn't say what
             kind of test to write.
================================================================================

WHAT THE PRD SAYS (story 15.5)

At the bottom of story 15.5 (ChatRoomScreen), the last AC line reads:

  "Add a fixture test that constructs the nested navigate call and
   asserts the params flow through."

This is to prove that story 15.7's `onSayHi` handler can call
`navigation.navigate('Chat', { screen: 'ChatRoomScreen', params: { friendUserId } })`
from inside the Menu stack (where MyProfileScreen lives) and land on
ChatRoomScreen in the Chat stack with the correct params.

WHY IT NEEDS SHARPENING

There are two very different ways to write this test:

  1. Unit test with a spy: `const nav = { navigate: jest.fn() };`
     — trivial to write, but only tests that the callback fires with
     the right arguments. It does NOT verify that the navigation
     actually works end-to-end (the params could still be malformed
     for the real navigator, and you'd never know).

  2. Integration test with a real NavigationContainer scaffold: build
     a tiny app tree with a real Tab.Navigator + two Stack.Navigators,
     press a stub button that fires the nested navigate call, and
     assert that the target screen renders with the correct params.
     Phase 14 uses this exact pattern in
     __tests__/navigation/MenuStack.test.tsx and
     __tests__/features/bookmarks/ExploreStack.test.tsx.

ANALOGY

"Add a test that proves the doorbell works" — do you (1) fake the
doorbell and check that pressing the button plays a MP3 file, or
(2) actually wire the button to a real doorbell and listen for a ring?
Both are valid, but they answer different questions.

FIX OPTIONS

  (a) Real-navigator scaffold (matches phase 14 pattern).
      + Actually verifies the nested navigation. Reuses an established
        test pattern in the repo.
      - Slightly heavier test setup.

  (b) Spy on navigation.navigate.
      + Fast to write. Zero setup.
      - Does not verify that the nested params structure is correct
        for the real navigator.

  MY RECOMMENDATION: (a). Phase 14 already has the pattern boilerplate
  copy-paste-ready. Verifies the real behaviour.
  
  ANSWER: okay go with option a

SHARPEN 3 — The `.md` sidecar next to the seed JSON is a new convention.
             We already have a repo pattern for annotating fixtures.
================================================================================

WHAT THE PRD SAYS (story 15.2)

The seed JSON's timestamps span "the last 3-4 days (relative to a
hard-coded base date so tests are stable)". JSON has no comments —
where does the base date get documented? The PRD says:

  "document the base date in a companion README fragment or an
   accompanying `.md` sidecar next to the JSON since JSON has no
   comments"

WHY IT NEEDS SHARPENING

Phase 12 solved the exact same problem in a different way: it stashed
metadata INSIDE the JSON in a specially-named block. Look at
`assets/dummyprofile.json` — it has a `__mutability_notes` field at
the top that explains editing rules. That pattern is already an
established convention in this codebase.

Adding a `.md` sidecar next to the JSON is a new convention no other
fixture in the repo uses. It creates a maintenance burden ("when I
edit chatMehvish.json, do I need to update the sidecar too?") and a
discoverability burden ("does this JSON have a sidecar? where?").

ANALOGY

You're writing a note on a package. You could scribble the shipping
instructions on the box itself (existing pattern) or attach a
Post-it note stuck to the outside that could fall off (proposed
`.md` sidecar). Both work, but the in-box option is what everyone
else in the warehouse already does.

FIX OPTIONS

  (a) Put the base date INSIDE chatMehvish.json under a `_meta` block.
      { "_meta": {
          "base_timestamp_ms": 1756944000000,
          "description": "Base date for stable test timestamps."
        },
        "messages": [ ... ]
      }
      + Consistent with __mutability_notes precedent from phase 12.
      + Zero risk of the sidecar going missing.
      - Storage helper has to skip the `_meta` key when parsing (or
        the seed reader has to grab `.messages` instead of the root).

  (b) `.md` sidecar as the PRD currently suggests.
      + No JSON schema change.
      - New convention. Two files to keep in sync.

  MY RECOMMENDATION: (a). Aligns with existing repo pattern. Storage
  helper reads `.messages`, tests only care about actual message data.

  ANSWER: okay go with option a, but we dont know what timestamps backend may use, so we may have to change this later, keep that in mind

SHARPEN 4 — MessageBubble test assertions on styles could be flaky.
================================================================================

WHAT THE PRD SAYS (story 15.5)

Sent messages sit on the right with theme.colors.accent.primary background;
received messages sit on the left with theme.colors.bg.surface. The AC
for tests says:

  "sent messages have `alignSelf: flex-end` and
   `theme.colors.accent.primary` background (assert via style prop or
   testID + rendered style)"

WHY IT NEEDS SHARPENING

React Native Testing Library flattens style props unpredictably. A
component like:

    <View style={[styles.bubble, { alignSelf: 'flex-end' }, extraStyle]} />

can render as `props.style === Array<[{}, {}, {}]>` or as a merged
`{}` depending on which internal flattener runs. Tests that read
literal style values often break when a maintainer refactors the
style composition — the runtime behaviour is unchanged, but the test
suddenly sees an array instead of an object.

ANALOGY

Testing the alignment of a sent message by inspecting its raw CSS is
like verifying "this car is red" by measuring the wavelength of light
reflecting off its bumper — technically correct but wildly brittle.
Better to check "this car has a `sent-message` label on its door".

FIX OPTIONS

  (a) Semantic testIDs.
      Give MessageBubble a `testID` that reflects its semantic role:
      `bubble-sent` for sender==='me', `bubble-received` for
      sender==='friend'. Tests query for the right testID; they don't
      touch style props.
      + Fast, resilient to internal style refactors, clear intent.
      - No downside.

  (b) Literal style prop assertions.
      + Directly verifies the visual outcome.
      - Flaky. Breaks on internal refactors that don't change UX.

  MY RECOMMENDATION: (a). testIDs already used everywhere in the repo;
  keep this consistent.

  ANSWER: okay go with option a

SHARPEN 5 — DevTriggersPanel design in 15.6 should be slot-based so 15.7
             can append without editing 15.6's file.
================================================================================

WHAT THE PRD SAYS

Story 15.6 creates the DevTriggersPanel component with ONE trigger
button (the IncomingRequestModal button, using Qurat as the fixture).
Story 15.7 says:

  "Add the second button 'Trigger RequestAcceptedModal (Mehvish)' to
   the `DevTriggersPanel` created in 15.6."

Story 15.6 also says: "design the panel so 15.7 only has to append."

WHY IT NEEDS SHARPENING

There are two ways to "append":

  1. If the panel hard-codes one button in its JSX, story 15.7 has to
     open the file created in story 15.6 and edit it.
  2. If the panel accepts children (a slot), story 15.7 just adds a
     second `<TriggerButton />` sibling in MyProfileScreen's JSX
     without touching DevTriggersPanel.tsx.

The second option is cleaner for the story boundary and makes 15.7's
diff strictly additive.

ANALOGY

Story 15.6 is building a bulletin board. Story 15.7 wants to pin a
second flyer. Option 1: story 15.7 rips the board off the wall,
adds a slot for the new flyer, re-hangs it. Option 2: story 15.6
built the board with a pinboard surface from day one; story 15.7
just pins the flyer.

FIX OPTIONS

  (a) DevTriggersPanel accepts children (slot).
      Panel renders: section heading + description + {children}.
      MyProfileScreen composes both buttons as siblings inside the
      panel. 15.6 ships with one child button. 15.7 appends a second.
      + Clean append, no cross-story file edits.
      - Slightly more component surface (accepts children prop).

  (b) Panel hard-codes button(s) internally.
      + Simpler component.
      - 15.7 has to edit 15.6's file.

  MY RECOMMENDATION: (a). Small design nudge, big cleanliness win.
  ANSWER: okay go with option a
