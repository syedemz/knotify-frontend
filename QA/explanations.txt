================================================================================
PHASE 12 BRAINSTORM — LAYMAN EXPLANATION OF THE PROBLEMS FOUND
================================================================================

Before I dispatch anyone to write phase-12 code, I re-read the PRD and cross-
checked it against the actual codebase. I found 5 real problems (blockers)
and 4 smaller ones (sharpen). Below is each one, written plainly, with an
analogy where useful. At the end of each item I list the possible fixes so
you can pick one — or write your own.

Underlying vocabulary refresher (skip if you already know it):

  - "PRD"        = the phase-12 plan file at
                   implementationplan/phase-12-landing-profile.md
  - "story"      = one numbered task inside that plan (12.1, 12.2, ... 12.6)
  - "AC"         = "acceptance criteria" — the checklist inside each story
                   that says "this story is done when X and Y and Z are true"
  - "type"       = a TypeScript declaration that says "an object of this
                   kind has field A of type string, field B of type
                   number", etc. It's a contract the code enforces.
  - "fixture"    = a fake data file we use during development instead of
                   real backend data
  - "component"  = a piece of the UI that renders itself (a button, a
                   section, a card)


================================================================================
BLOCKER 1 — The dummy profiles have a "siblings" field but our profile
            data structure doesn't allow it.
================================================================================

WHAT THE PRD ASSUMES
--------------------
Story 12.1 says: "create dummyfemale.json with two siblings in it, and
dummyprofile.json with an empty siblings list". Story 12.2 says: "the
SiblingsSection component reads `profile.siblings[]` and renders one card
per sibling."

WHAT THE CODE ACTUALLY SAYS
---------------------------
Our master definition of what a user profile IS lives in
`src/types/api/UserProfile.ts`. Think of it as the official passport
template for user data — every field the backend can hand us is listed
there. That file does NOT have a `siblings` field. It has first_name,
last_name, religion, city, job_title, etc., but no siblings.

Siblings only exist inside the ONBOARDING draft (the temporary scratchpad
during registration). Once registration is done, siblings currently vanish
from the user profile shape — the real backend column for siblings does
not exist yet.

ANALOGY
-------
Imagine you're filling out an insurance form. There's a section on the form
called "spouse". Halfway through you write down your spouse's name, but
when the clerk copies your form into the official filing cabinet, that
filing cabinet's folder-template has no "spouse" slot. So it gets lost —
or worse, the whole form gets rejected because it has an extra field the
template doesn't allow.

That's what happens here. The dummy JSON has `siblings: [...]` but the
TypeScript type says "no such thing as siblings on a user profile". The
compiler will complain, the test will fail, and the SiblingsSection
component will not compile because `profile.siblings` isn't a legal
expression.

WHY THIS MATTERS
----------------
Story 12.2 requires a SiblingsSection component that reads `siblings[]`
and a test that asserts "the female fixture has 2 siblings and the own-
profile fixture has 0 siblings". If we can't legally put siblings on the
profile object, none of that works.

FIX OPTIONS
-----------
  (A) Add an optional `siblings` field to the two "dummy" types the PRD is
      already creating (DummyFemaleProfile and DummyOwnProfile). This is
      the smallest change and matches what the PRD is already trying to
      do — the PRD just forgot to list this field alongside `photos` and
      `faceSelfieUri`. The fixture files stay as-is; only the type files
      need one extra line.

      Cost: tiny. Downside: none — we always knew siblings was a
      client-side concern for now.

  (B) Add `siblings` to the real UserProfile type. Bigger change; assumes
      the backend WILL add a siblings column. Overreaches into future
      backend scope.

  (C) Remove siblings from the phase entirely. Drop SiblingsSection. Wait
      until the backend supports it.

  RECOMMENDATION: (A). It's what the PRD meant to say and forgot.
  ANSWER: A, but eventually we will add siblings too because in the backend the siblings is another table
  where the primary key is the user id

BLOCKER 2 — Story 12.4 calls a function `showSnackbar()` that doesn't
            exist in our codebase.
================================================================================

WHAT THE PRD ASSUMES
--------------------
Story 12.4 says: "each of the four round action buttons (X / undo / star /
✓) has an onPress that calls `showSnackbar(t('landing.actionUnavailable'))`."
And the test says "assert that the showSnackbar mock was called".

WHAT THE CODE ACTUALLY SAYS
---------------------------
We have a Snackbar COMPONENT (`src/components/Snackbar.tsx`). But it's not
a function you can call from anywhere. It's a React component you have to
render, and you have to give it a `visible` prop (true/false) and a
`onDismiss` handler.

Look at how the existing code uses it (Page25PersonalityTraitsScreen for
example): the screen keeps a local piece of state called
`isSnackbarVisible`. When something happens, it sets that to true.
Somewhere in the JSX, `<Snackbar visible={isSnackbarVisible} ... />` is
rendered. When the user dismisses it, the state flips to false.

There is NO global `showSnackbar("hello")` helper anywhere in the codebase.
There is no SnackbarProvider or context that would let you call it from
outside a component.

ANALOGY
-------
It's like the PRD says "press the buzzer at the front desk." But there is
no buzzer. There's a bell you have to hold in your hand and ring yourself,
and there's no central switchboard.

To make `showSnackbar()` work, someone would have to first build the
buzzer + switchboard (a global provider + hook) — which is a real,
cross-cutting piece of infrastructure, not something to slip into a
landing-screen story.

WHY THIS MATTERS
----------------
As written, story 12.4 either (a) silently expands scope into "build a
global Snackbar provider from scratch" without saying so — which is a
sizeable side-quest and touches every screen going forward — or (b) the
subagent writes code that references a function that doesn't exist and
the whole story fails to compile.

FIX OPTIONS
-----------
  (A) Use the local-state Snackbar pattern already used elsewhere. Rewrite
      story 12.4's AC to say: "MarriageLandingScreen holds a local
      `snackbar: string | null` state. Each action button setter sets it
      to `t('landing.actionUnavailable')`. A <Snackbar visible={...}> is
      rendered at the screen root, showing the current message. Test
      asserts the toast text appears after pressing the ✓ button." No new
      infrastructure, matches the pattern Page25 and Page30 already use.

      Cost: tiny. Downside: none.

  (B) Split "add global Snackbar provider" into its own story (probably
      needs a small utility phase later or a story 12.0). Then 12.4 can
      call `showSnackbar()`. This is the "right" long-term architecture
      but is more work and drags in a cross-cutting concern this phase
      shouldn't own.

  (C) Leave story 12.4 as-is and let the subagent invent something.
      Guaranteed rework — DO NOT PICK THIS.

  RECOMMENDATION: (A). Matches existing convention, zero scope creep.

  ANSWER: Option A

BLOCKER 3 — Story 12.4 references a Jest mock that doesn't exist.
================================================================================

WHAT THE PRD ASSUMES
--------------------
Story 12.4 says: "Animation is NOT tested (Reanimated worklets are mocked
to no-op per the existing `__mocks__/react-native-reanimated` setup)."

WHAT THE CODE ACTUALLY SAYS
---------------------------
The `__mocks__/` folder contains mocks for three libraries:
react-native-vision-camera, react-native-vision-camera-face-detector, and
react-native-worklets-core. There is NO
`__mocks__/react-native-reanimated` file. Nothing anywhere sets up a
Reanimated mock.

Reanimated is the library that powers the smooth slide-up / slide-down
animation of the bottom action bar. It runs animations on a separate
"worklet" thread that Jest (the test runner) can't handle without a mock.

ANALOGY
-------
Imagine the PRD says "the crash-test dummy is already sitting in the
driver's seat, ready for the safety test." But when you open the car
door, there's no dummy. You can't run the safety test without one, and
if you press the button anyway, the entire car goes into an error state.

WHY THIS MATTERS
----------------
The moment a test imports MarriageLandingScreen (which is required by
story 12.4's screen wiring test), Jest also loads the CollapsingActionBar
which imports Reanimated. Without the mock, the test either crashes with
a cryptic error or floods the terminal with worklet warnings that make
the CI output unreadable. Either way the phase can't be signed off
because the test suite goes red.

FIX OPTIONS
-----------
  (A) Add a one-liner to jest.setup.ts (or wherever Jest's global setup
      lives):
        `jest.mock('react-native-reanimated', () =>
          require('react-native-reanimated/mock'));`
      Reanimated ships an official mock. This is the standard idiom.
      Add this to story 12.4's AC.

      Cost: one line. Downside: none.

  (B) Skip the screen wiring test that mounts MarriageLandingScreen and
      only test the sub-components (HeaderBar, etc.) directly. Weaker
      test coverage but works around the mock issue.

  RECOMMENDATION: (A). Standard practice, no downside.
  ANSWER: Option A

BLOCKER 4 — Story 12.4 creates a `CandidateHero` component that
            duplicates the `HeroBlock` component from story 12.2.
================================================================================

WHAT THE PRD ASSUMES
--------------------
Story 12.2 creates HeroBlock inside `src/features/profile-sections/`. It
knows about two variants — 'other' (for viewing a candidate) and 'self'
(for viewing your own profile). When variant is 'other', it renders the
big full-bleed photo, the Active-today / Gold overlay bubbles, and the
name / age / country-flag / job-title chip strip. This is exactly the
landing page hero.

Story 12.4 THEN creates a SECOND component in a different folder called
CandidateHero. It's described as "full-bleed hero image (first photo),
the two overlay bubbles ("Active today" / "Gold" — guarded), and the
name / age / green-tick / city-and-country / country-flag / profession
chip strip beneath." That is word-for-word what HeroBlock('other') does.
The story then says "delegates to HeroBlock in the section catalog for
the actual chip strip", which reveals the confusion — CandidateHero
would just wrap HeroBlock and add nothing.

MEANWHILE — MarriageLandingScreen (also in 12.4) uses
`<ProfileScrollView profile={dummyfemale} viewer="other" />` — and
ProfileScrollView already renders HeroBlock at the top of its scroll.

So there are two possibilities:
  (i)  MarriageLandingScreen renders BOTH `<CandidateHero />` AND
       `<ProfileScrollView>` — the hero image appears twice on the page.
  (ii) MarriageLandingScreen only uses one of them and the other is dead
       code no one imports.

ANALOGY
-------
It's like a wedding invitation with two identical envelopes stacked
together. Either the guest sees two invitations (confusing) or one of
the envelopes was extra material the designer never intended to hand out.
Neither is what we wanted.

WHY THIS MATTERS
----------------
If the subagent picks interpretation (i), the landing page has a visual
bug (double hero). If (ii), we've paid to build something that ships
dead-on-arrival. Either way we look sloppy.

FIX OPTIONS
-----------
  (A) Delete CandidateHero from story 12.4 entirely. HeroBlock inside
      ProfileScrollView already handles the landing hero in the 'other'
      variant. MarriageLandingScreen composes exactly three things:
      HeaderBar + ProfileScrollView + CollapsingActionBar. Cleaner.

      Cost: shrink story 12.4. Downside: none.

  (B) Keep CandidateHero and remove HeroBlock's 'other' variant. Split
      the responsibility differently. More work, no real benefit.

  RECOMMENDATION: (A). Delete the duplicate.
  ANSWER: Option B

BLOCKER 5 — Story 12.4's "row 2 = bottom tab bar navigation" is
            ambiguous. Two possible implementations, only one is right.
================================================================================

WHAT THE PRD ASSUMES
--------------------
Story 12.4 describes CollapsingActionBar as "bottom overlay with two rows:
row 1 = four round action buttons (X / undo / star / ✓); row 2 = the
bottom tab bar navigation. Only row 2 collapses on scroll."

WHAT THE CODE ACTUALLY SAYS
---------------------------
React Navigation already provides the bottom tab bar via `AppTabs.tsx`
(the thing story 12.6 renames to Marriage/Explore/Chat/Menu). It renders
at the bottom of every tab-hosted screen automatically. It is NOT part of
any individual screen — it belongs to the navigator.

The PRD says row 2 IS the tab bar. Two ways to read that:

  Interpretation (i) — Hide the native tab bar entirely, then draw a
  custom lookalike inside the screen as row 2 of CollapsingActionBar.
  Then when we scroll down, the custom row-2 slides away. Downside: we
  now maintain two tab-bar implementations, and switching tabs from the
  landing screen becomes non-trivial (we'd have to wire the custom
  row-2 buttons to React Navigation manually).

  Interpretation (ii) — The native tab bar STAYS. CollapsingActionBar is
  just the four action buttons (row 1). When we scroll down, we animate
  the native tab bar itself (via React Navigation's `tabBarStyle` +
  Reanimated). This is the standard idiom and doesn't require any
  custom tab-bar code.

ANALOGY
-------
It's like the PRD says "put a second steering wheel in the passenger
seat". Do you (i) rip out the driver's wheel and put both new wheels in?
Or (ii) leave the real wheel where it is and treat the "passenger wheel"
as decoration? The PRD doesn't say, and the two answers lead to very
different builds.

WHY THIS MATTERS
----------------
The subagent could go either way. Interpretation (i) is a much bigger
job and probably wrong (React Navigation's tab bar is battle-tested; we
shouldn't reinvent it). Interpretation (ii) is easy and idiomatic.

FIX OPTIONS
-----------
  (A) Rewrite the AC to explicitly say: "CollapsingActionBar contains
      ONLY the four round action buttons (row 1). The bottom tab bar is
      the native React Navigation tab bar. When MarriageLandingScreen
      detects a downward scroll (>8px delta), it animates the native
      tab bar via `screenOptions.tabBarStyle` — translateY = tabBarHeight
      / opacity = 0. On upward scroll, it animates back. Reanimated
      shared value + useAnimatedStyle handles this."

      Cost: rewrite one AC. Downside: none — this is the standard idiom.

  (B) Rewrite the AC to say "build a custom bottom tab bar inside
      CollapsingActionBar, hide the native one via
      `tabBarStyle: { display: 'none' }`, wire tab switches manually via
      `useNavigation`". More work, more risk, replaces something proven
      with something new.

  RECOMMENDATION: (A). Standard idiom, keeps React Navigation in charge.
  ANSWER: Option A

SHARPEN 8 — Story 12.1 leaves `preferences.personalityTraits` as
            "unknown", which forces every reader to cast.
================================================================================

Our UserProfile type defines `preferences: Record<string, unknown> | null`
— which means TypeScript sees it as "some object I know nothing about".
Every place that reads `preferences.personalityTraits` has to cast it,
like: `(prefs as { personalityTraits: string[] }).personalityTraits`.

The existing Page25 screen already does this. Story 12.2's
PersonalitySection would have to do it again. Casts spread bugs — if the
shape ever changes, only the cast site knows about it.

FIX OPTIONS
-----------
  (A) Narrow `preferences` in DummyFemaleProfile / DummyOwnProfile to a
      typed shape:
        `preferences: { personalityTraits?: string[] } &
                       Record<string, unknown> | null;`
      Then PersonalitySection reads `.personalityTraits` with no cast.

  (B) Leave as-is. Small nuisance, not a blocker.

  RECOMMENDATION: (A). Tiny typing addition, cleaner reads.
  ANSWER: Option A
