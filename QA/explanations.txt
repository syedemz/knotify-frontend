ISSUE 1 — SEVERITY: BLOCKER
    "The sibling record has 3 fields; the plan wants us to fill 5"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
    Story 7.2 says each sibling entry captures five things:
        name, gender, sibling_age, marital_status, profession

WHY IT MATTERS
    Think of the app's "sibling notebook" as a form with only 3 lines:
        Line 1: Name
        Line 2: Age
        Line 3: Marital status
    The plan is telling us to write "Gender" and "Profession" on the form,
    but there are no lines for them. The form has to be redesigned first —
    someone has to add two new lines before we can fill them in.

    That "form" is a TypeScript type called `SiblingDraft` in
    `src/features/onboarding/draftSchema.ts`. Right now it only has name,
    age, and maritalStatus. As long as the type is missing fields, the code
    will not compile if you try to write a `gender` or `profession` value
    into it. This is a hard stop — the phase cannot ship until we fix it.

    There's a secondary wrinkle. The draft file has a "schema version"
    number stamped on it (currently version 1). If we add two new fields,
    that's a shape change, and the convention says we should bump it to
    version 2. The doc comment on the file explicitly says:

        "When bumping, decide before merge whether to migrate, discard,
         or prompt."

    Translation: if a real user has a half-finished draft saved on their
    phone under the old shape (version 1) and the app updates to a new
    shape (version 2), what happens when they open the app?

      - "migrate" = automatically add the two new empty fields to their
                    saved draft and keep going where they left off
      - "discard" = throw their saved draft away and send them back to
                    page 1 to start over
      - "prompt"  = show them a dialog: "your saved progress can't be
                    loaded, start over?"

YOUR CHOICES
    A) [RECOMMENDED] Extend the type inside story 7.2 (add gender +
       profession fields) AND bump schemaVersion 1 → 2 with the DISCARD
       policy. Reason: this is pre-launch. Nobody is on the real app yet.
       Discard is 5 lines of code; migrate is 30+ lines you'll delete
       before launch anyway.
    B) Extend the type AND bump schemaVersion with the MIGRATE policy.
       More work, no user-visible benefit right now.
    C) Extend the type but DO NOT bump schemaVersion. Fastest, but breaks
       the convention documented in the file itself. If we bump later
       (which we will, for real launch), we'll owe a proper migration
       policy then.
    D) Drop `gender` and `profession` from story 7.2 AC-2. Simplest, but
       the user then can't record their siblings' gender or profession
       anywhere — matchmaking-quality data lost.

  ANSWER: Option A

ISSUE 2 — SEVERITY: HIGH
    "What does Page 19 look like when you come BACK to it?"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
    Page 19 has three states:
      - Initial:  "How many siblings do you have?" (a number input)
      - Filling:  N sibling cards visible, fill each one in
      - Complete: All valid, Continue button lit up

    The plan describes moving forward through those states. It says
    nothing about what happens when you go BACKWARD to the page.

WHY IT MATTERS
    Imagine you filled out a paper form: "I have 3 siblings" → then filled
    in all 3 boxes → moved to the next page. Now you tap the back arrow.
    You're back on the siblings page. What do you see?

      - A blank number input? (Feels broken — "wait, I already did this")
      - The 3 filled-in boxes ready to edit? (Matches expectation)
      - A "you already have 3 siblings, edit them?" prompt? (Extra tap)

    Every other page in the wizard re-hydrates from your saved data when
    you back-nav. Page 13 (education credentials) is the closest cousin —
    it fills all the fields back in from the draft. Page 19 should
    probably do the same, but the plan doesn't say so.

YOUR CHOICES
    A) [RECOMMENDED] On mount, if the draft already has siblings saved:
       open in Filling state with the cards pre-populated. If the count
       was 0 (user explicitly said "no siblings"): open in Complete state
       with Continue lit. Only open in Initial state if the user has
       never been to this page before.
    B) Always open in Initial state (blank count). User has to redo the
       count and re-fill every time they back-nav. Simple, annoying.
    C) Open in a hybrid state: show the count as a read-only badge
       ("You said: 3 siblings") plus the filled cards. Extra design work.

ANSWER: Go with Option A

ISSUE 3 — SEVERITY: HIGH
    "What counts as a valid 'profession' for a sibling?"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
    Story 7.2 AC-2:
        `profession (max 35, sanity rule)`

WHY IT MATTERS
    "Sanity rule" is not an instruction — it's a hand-wave. There are two
    kinds of validators in the codebase:

      - `isValidName` (from phase 3): allows letters, spaces, hyphens,
        apostrophes only. Rejects numbers, punctuation, ampersands, etc.
        Max 35 characters. Meant for people's names.

      - `isValidOfficeAddress` (from phase 4): only checks max length.
        Allows any characters (numbers, slashes, hashes, etc.). Meant for
        freeform text like "Flat 4B, 12/A Rajbagh".

    Profession sits between these. "Engineer" passes both. But:
      - "Ph.D. researcher" fails `isValidName` (periods)
      - "Marketing & Sales" fails `isValidName` (ampersand)
      - "Software Engineer II" fails `isValidName` (digit)

    If we use `isValidName`, a lot of real-world job descriptions get
    rejected and users get frustrated. If we use `isValidOfficeAddress`,
    someone can type "@#$%" as a profession and it goes into the database.

YOUR CHOICES
    A) [RECOMMENDED] Use whatever validator we pick for the parent-job
       fields on Page 18 (see Issue 4). Both are jobs; same rules should
       apply. Update Story 7.2 AC-2 to say `use isValidParentJob`
       (or whatever name we settle on).
    B) Use `isValidName` (strict): letters, spaces, hyphens, apostrophes
       only. Cleanest data, most user rejections.
    C) Use `isValidOfficeAddress`-style (loose): only enforce max length.
       Most permissive, allows garbage.
    D) Create a new `isValidProfession` validator: allow letters, spaces,
       hyphens, apostrophes, ampersands, periods, digits. Most work,
       best fit for the data.
    
    ANSWER: Go with option D

ISSUE 5 — SEVERITY: MEDIUM
    "Will the backend accept the words 'YES' and 'NO' in all caps?"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
    Story 7.1 AC-2 uses `options.yesNo` for the "is your father retired?"
    and "is your mother retired?" questions. That options file contains
    exactly two values: ["YES", "NO"] — uppercase.

WHY IT MATTERS
    Think of the backend as a strict receptionist with a checklist. When
    you say "father retired: YES", they check their list to see if "YES"
    is one of the allowed answers. If their list actually says
    "Yes" / "No" (capital Y, lowercase e-s), or "Retired" / "Working",
    they'll reject the whole form.

    Right now, nobody has verified what the backend's list actually says.
    The `father_retired` column in the database is a plain TEXT column,
    so on paper it accepts anything. But there may be a check constraint
    (a rule saying "only these exact values allowed") that we haven't
    looked at.

    This is NOT a blocker for phase 7 — phase 7 only writes to the
    draft on your phone, not to the backend. The backend PATCH doesn't
    happen until phase 11 (the final "submit everything" step). But if
    we discover the casing is wrong at phase 11, we'll be re-touching
    every YES/NO input in the whole wizard. Better to catch it now.

    Related note for later: `has_children` and `move_abroad` also use
    `options.yesNo` in phases 8 and 9, but the database stores those as
    booleans (true/false), not text. So those two need a string→boolean
    conversion at PATCH time regardless of what we decide here.

YOUR CHOICES
    A) [RECOMMENDED] Add an "unvalidated assumption" note to phase 11's
       PRD saying "verify backend accepts YES/NO uppercase before wiring
       the PATCH". Ship phase 7 as planned. Fix casing later if needed.
    B) Check the backend right now (grep `knotify-backend` for the
       column's check constraint, or ask the backend team). Adds delay
       to phase 7 for a question that doesn't need answering yet.
    C) Change `options.yesNo` to "Yes"/"No" (title case) preemptively.
       Might be right, might be wrong — coin flip without checking.

ANSWER: Option A

ISSUE 6 — SEVERITY: MEDIUM
    "What does 'Cancel' do if you already saved siblings before?"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
    Page 19 has a Cancel button in the Filling state. The plan says
    "Cancel returns to Initial with blank count."

WHY IT MATTERS
    Imagine you filled out the sibling page yesterday with 3 siblings.
    Today you come back, back-nav to Page 19 (per Issue 2 we decided to
    show your saved cards). You edit one field, then change your mind
    and tap Cancel. What should happen?

    Two readings of the plan:

      (a) Cancel discards ONLY today's edits. Your 3 saved siblings from
          yesterday are still there — you just haven't changed them.
          (Matches "undo my current changes" — what most apps do.)

      (b) Cancel wipes both today's edits AND yesterday's saved siblings.
          You're back at "how many siblings do you have?" with nothing.
          (Matches "start this section over from scratch" — nuclear.)

    The plan is ambiguous. The subagent will pick one; if they pick (b)
    and you meant (a), users lose data.

YOUR CHOICES
    A) [RECOMMENDED] Cancel only discards in-progress local state; it
       does NOT touch the previously-saved siblings in the draft.
       If the user wants to fully redo, they can back-nav and go
       forward again.
    B) Cancel wipes everything. Simpler code, worse UX.
    C) Cancel shows a confirmation ("Discard your 3 siblings?") — extra
       design work, more flexibility.

    ANSWER: OPtion A

ISSUE 7 — SEVERITY: LOW
    "When exactly does 'I have 0 siblings' get saved?"
--------------------------------------------------------------------------------

WHAT THE PLAN SAYS
    Story 7.2 AC-3:
        "Value `0` in the count input immediately enables Continue and
         writes an empty siblings array."

WHY IT MATTERS
    The word "immediately" is doing a lot of work here. Two readings:

      (a) The moment the user types "0" in the count box, the app writes
          an empty array to the draft (before they tap Continue).
      (b) When the user types "0", the Continue button lights up
          immediately, but the write to the draft only happens when
          they actually tap Continue (like every other page).

    Reading (a) creates a minor bug scenario: user types "0", changes
    their mind, types "3", now goes through the 3-sibling flow. In
    between there was an extra `setSiblings([])` write that got
    overwritten. Not broken, but noisy — extra writes to secure storage.

    Reading (b) matches every other page's pattern: writes happen on
    Continue tap, never on input change.

YOUR CHOICES
    A) [RECOMMENDED] Reading (b). "Immediately" refers only to the
       button state (lights up right away), not the write. Write happens
       on Continue tap like every other page. Consistent, no wasted
       writes.
    B) Reading (a). Write happens on input change. Matches a literal
       reading of "immediately" but breaks the pattern.

ANSWER: Option A
